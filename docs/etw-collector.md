# Отдельный ETW-сборщик

Реализован самостоятельный сборщик и клиент локального канала. Сборщик не подключён
к SessionManager: TimeTracker пока использует polling 5 s. Это следующий компонент
этапа 5, после проверки доступности ETW. Установка службы и автозапуск отсутствуют.

## Проверка с разными уровнями прав

VS Code и TimeTracker остаются обычными процессами. Открыть отдельный PowerShell
от имени администратора **того же пользователя Windows**, перейти в проект и запустить:

```powershell
cd E:\Projects\TimeTracker
.\.venv\Scripts\python.exe tools/run_etw_collector.py --seconds 30
```

В течение 30 секунд запустить получателя в обычном терминале VS Code:

```powershell
.\.venv\Scripts\python.exe tools/check_etw_collector.py
```

Сборщик ждёт подключения до 30 секунд, затем открывает ETW-сессию на заданное время.
Получатель сам запускает два невидимых процесса с ожиданиями 0,3 и 2 s. Он проверяет
start/stop, точное совпадение CreateTime с GetProcessTimes через сохранённый handle,
наличие пути в start, непрерывность потока и отсутствие зарегистрированных потерь.
Клики и переключения окон не нужны. Результат — `Passed: True`, код выхода 0,
отчёт `build/etw-collector/<timestamp-id>/report.json`. В отчёте получателя
`reader_elevated` должен быть false. Отчёт сохраняет только собственные события
помощников без путей; чужие события представлены счётчиками.

Для параллельной независимой проверки можно передать одинаковый `--channel NAME`
обоим инструментам. Имена ограничены ASCII буквами, цифрами, `_` и `-`, 1..64 символа.
Один канал обслуживает одного получателя. Срок сессии — 3..86400 s, по умолчанию 60 s.
Ctrl+C, отключение получателя и ошибка источника завершают сборщик с cleanup.
Ничего не устанавливается, права учётной записи и параметры UAC не меняются.

## Состав

- `platform/windows/etw.py`: OpenTrace/ProcessTrace, TDH-декодирование по именам
  свойств, поток чтения, защищённая блокировкой очередь до 4096 записей.
  Диагностический импорт сохранён через совместимый модуль.
- `etw_collector.py`: управление собственной временной ETW-сессией через системный
  `logman.exe` с абсолютным путём. Provider Kernel-Process, keyword 0x10, level 4,
  flush 1 s, буферы 64 KiB, минимум 2, максимум 16. Имя сессии содержит UUID.
  Утилита не ищется через PATH; ETL и постоянный Data Collector Set не создаются.
- `event_pipe.py`: односторонний named pipe. DACL разрешает текущего пользователя
  и SYSTEM, удалённые клиенты запрещены, второй владелец того же канала не допускается.
  Получатель открывает только чтение и не разрешает серверу impersonation.
  Сборщик не принимает команд и не выполняет действия от имени получателя.
- `event_stream.py`: проверка версии протокола, поколения и последовательности
  сообщений/событий. Ошибка либо пропуск делают поток неполным до нового поколения.

Локальный пользователь является границей доверия: доступ имеют процессы того же
пользователя, а не только конкретный exe TimeTracker. Запуск под другой учётной записью
и будущая служба SYSTEM требуют отдельной настройки целевого SID/канала.

## Протокол и завершение

Фрейм: uint32 little-endian длина + UTF-8 JSON, максимум 2 MiB. Нет pickle.
Последовательность: `ready`, `batch` каждые 250 ms или при оставшейся очереди,
`draining` после остановки источника, затем `stopped`. В пакете максимум 8 событий.
При ошибке инструмент пытается передать `error`; разрыв канала также означает отказ.
Синхронные вызовы клиента используют overlapped I/O с конечным ожиданием;
медленный читатель ограничен таймаутом записи 2 s. Отмена I/O дожидается завершения
работы ядра с буфером и OVERLAPPED. После неполного фрейма канал закрывается.

В каждом событии сохраняются sequence, PID, исходное время события и время его
получения в наносекундах Unix. CreateTime сохраняет точность 100 ns. ImageName из
start передаётся как есть, без открытия уже завершившегося процесса. Это ещё не
канонический DOS-путь: нормализация пути и перевод identity к точности текущего
домена относятся к интеграции. Отсутствие ImageName в stop допустимо; отсутствие
identity либо пути в start отмечает неполноту источника.

`ready` означает открытие consumer и не обещает полноту предшествующей истории.
`started_at_ns` — начало попытки запуска, не подтверждённая граница покрытия.
`healthy` означает живой источник без зарегистрированного сбоя;
`data_complete` — отсутствие известных потерь/ошибок декодирования, включая хвост
после штатной остановки. Отсутствие зарегистрированных потерь не доказывает полноту
само по себе. Счётчики потерь и overflow накопительные. Автоматического reconnect
пока нет: повторный запуск создаёт новое поколение, которому требуется snapshot.

При штатном выходе сначала останавливается собственная ETW-сессия, затем consumer
дочитывает буферы, освобождается handle и отправляется хвост очереди. При ошибке
транспорта сессия также останавливается. Принудительное убийство/сбой процесса
не гарантирует выполнение finally: оставшаяся сессия потребует остановки по её
точному имени. Автоматическая очистка чужих/старых сессий не выполняется.

## Проверено и что осталось

2026-09-10: 45 тестов прошли (24 сборщика/IPC, 8 ETW probe, 13 WMI probe).
Проверяются реальные локальные Windows pipe handles, ACL, запрет записи клиенту,
таймауты accept/read/write, частичный фрейм, отключение, конфликт владельцев,
cleanup при отказе прав/источника/транспорта, TDH, точность identity, сохранение пути,
потери и поколения. Подписка ETW для этих тестов не открывается.

Запуск двух отдельных процессов без повышения прав также проверен:
`build/etw-collector/20260910T162904Z-416e1cbe/report.json`. Получатель получил
`ETW start failed: 0x80070005`, инструменты завершились с кодом 1.
Повышенный сборщик с обычным получателем успешно проверен пользователем:
`build/etw-collector/20260910T163358Z-2318677c/report.json`, `passed=true`,
`reader_elevated=false`. Получатель получил 229 событий (117 start, 112 stop),
что совпало со счётчиками источника и last_sequence=229. Ошибок, overflow,
потерь событий/буферов и пропусков CreateTime не зарегистрировано.

Оба помощника получены ровно по одной паре start/stop, CreateTime всех четырёх
событий точно совпал с GetProcessTimes, путь присутствует в обоих start.
Фактическая жизнь помощников — 347,955 и 2046,755 ms. Timestamp start отличается
от создания на +0,029–0,031 ms, timestamp stop от завершения — на +0,127–0,139 ms.
Задержка от timestamp до callback сборщика — 1,667–2,014 s; отдельный timestamp
получения клиентом не записывался, поэтому это не полная задержка ETW + IPC.
`missing_ImageName=22` при отсутствии `missing_start_image` допустим для stop.

Сборщик штатно завершился через 30,070 s, `cleanup_confirmed=true`.
`healthy=false` в финальном `stopped` ожидаем: источник уже остановлен.
CPU сборщика — 0,03125 s за этот интервал, около 0,104% одного ядра
или 0,0065% всей 16-поточной машины. CPU получателя округлился до 0,0 s;
это не доказательство нулевой стоимости. Прогон подтверждает работоспособность
отдельного сборщика и IPC между уровнями прав; нагрузка под частыми стартами,
сон/пробуждение и длительная работа требуют последующих проверок.

CPU-поля этого smoke — CPU соответствующего Python-процесса. У сборщика окно
охватывает запуск/чтение/остановку ETW и дочитывание, но не старт Python/импорты,
CPU дочернего logman и системные расходы. Это не итоговый A/B-замер эффективности.

Дальше: связать поток с начальным snapshot и worker, корректно учитывать поздние
границы сессий, PID reuse, потери и wake/reconnect. Только после этого переключать
здоровый источник на reconciliation 60 s с fallback 5 s и измерять общий CPU.

Нативные основания: [named pipes](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipes),
[CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea),
[жизнь OVERLAPPED при отмене](https://learn.microsoft.com/en-us/windows/win32/fileio/cancelioex-func).

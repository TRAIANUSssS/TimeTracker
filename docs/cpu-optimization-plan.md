## Цель и исходные данные

Снизить постоянную нагрузку CPU и задержки обработки оконных/системных событий,
сохранив учёт running/foreground во время IDLE, корректность PID reuse,
sleep/wake, lock/unlock, recovery и атомарность SQLite.

В прошлом обсуждении зафиксирован замер: 343 процесса, полный snapshot —
2,21 s wall time и 2,09 s CPU time, период — 5 s, 16 логических процессоров.
Это около 2,61% CPU всей системы только на snapshot. Наблюдавшиеся около 6%
для приложения целиком требуют отдельного воспроизводимого измерения.
Старый замер является ориентиром, не новой базовой линией.

Текущий код:

- `collector.py`: процессы каждые 5 s, foreground/idle и Kernel-Power каждые 2 s,
  heartbeat каждые 5 s.
- `platform/windows/processes.py`: повторные exe/create_time и очистка кеша psutil.
- `platform/windows/provider.py`: metadata по пути уже кешируются.
- `domain/session_manager.py`: state возвращает копию словарей; обработка события
  также копирует состояние и выполняет транзакцию.
- `storage/database.py`: новое подключение и проверка схемы на каждую транзакцию.
- `worker.py`: controller.tick и запись работают в отдельном потоке-владельце;
  `tray/tray_app.py` передаёт уведомления через ограниченную очередь.
- `platform/windows/power_history.py`: журнал перечитывается с начала run.

Последние четыре пункта — кандидаты для профилирования, не доказанные причины CPU.

## 1. Диагностика и воспроизводимый baseline — обязательно первым

Предусмотреть небольшой модуль `src/time_tracker/diagnostics/performance.py`
и отдельный runner `tools/benchmark_tracker.py`. Добавлен также генератор
читаемых отчётов `tools/report_benchmark.py`.

Модуль диагностики:

- Включается флагом, например `--perf`; по умолчанию подробные измерения отключены.
- Измеряет wall time через `perf_counter_ns`, CPU текущего потока через
  `thread_time_ns`. CPU всего процесса измеряется отдельно, поскольку он включает
  API и другие потоки. Вложенные стадии помечаются как inclusive/exclusive,
  чтобы не складывать одно время несколько раз.
- Стадии: перечисление PID, identity/create_time, exe, metadata/icons,
  foreground/title, idle/lock, Kernel-Power query/parse, копирование state,
  обработка событий, SQLite connect/schema/transaction/commit, весь collector tick.
- Счётчики: процессы, новые экземпляры, попадания в кеш, системные запросы,
  AccessDenied/NoSuchProcess, транзакции, события; позднее — очередь, задержки
  доставки, переполнения, переподключения и расхождения reconciliation.
- Агрегирует count/total/mean/p50/p95/max в ограниченной памяти; выгружает JSONL
  раз в 60 s и при штатном завершении. Для редких операций указывает размер выборки.
- Подробные замеры на каждый PID включаются только в коротком диагностическом
  прогоне. Постоянная диагностика не пишет строки для каждого процесса/события.
- Сохраняет версию/commit, dirty status, Windows, CPU и число логических процессоров,
  Python/psutil, режим сборки, интервалы, длительность сценария и число процессов.
- В отчёт не включаются window titles и содержимое пользовательских документов.

Runner:

- Для микрозамеров использует коллектор без записи пользовательской истории;
  для интеграционного прогона — отдельную тестовую БД и уникальный каталог отчёта.
- Может внешне наблюдать выбранный экземпляр приложения по PID + creation time,
  фиксируя CPU seconds, память, I/O, число потоков и handles с шагом 1 s.
- Показывает CPU seconds/minute и нормализованный CPU:
  `100 * delta_cpu_seconds / elapsed_seconds / logical_cpu_count`.
  Не смешивает 100% одного ядра и 100% всей машины.
- Не запускает второй пишущий экземпляр на пользовательской БД.
- При проверке WMI учитывает также изменение нагрузки WmiPrvSE; сравнение
  повторяется с подпиской и без неё при сопоставимой фоновой работе.

Протокол сравнения:

1. Отдельно измерить холодный запуск и прогретый режим.
2. Для baseline и каждого кандидата выполнить по три 10-минутных прогона
   спокойной системы с одинаковым сценарием; ACTIVE и IDLE учитывать раздельно.
3. Повторить сценарии переключений окон/вкладок, запуска/завершения процессов,
   включая короткие процессы, и открытия UI статистики.
4. Сравнить Python-запуск и portable exe. Проводить сравнение версий последовательно,
   чередуя исходную и изменённую версии, а не запускать их одновременно.
5. Проверить влияние самой диагностики: одинаковые прогоны с ней и без неё.
6. Если остаётся значительная необъяснённая доля CPU, снять короткий профиль
   cProfile; при необходимости — системную трассу Windows. Профилировщик не
   использовать для итогового приёмочного измерения CPU.

Результат этапа: baseline-отчёт с долями CPU, длительностями, задержками и
необъяснённым остатком; утверждения о горячих участках опираются на этот отчёт.

## 2. Ускорение текущего ProcessCollector — первая оптимизация

- Кешировать ProcessObservation по подтверждённой идентичности PID + creation time.
- Для известного экземпляра выполнять свежую проверку идентичности, использовать
  сохранённый путь и metadata; дорогое разрешение делать для новых/неразрешённых.
- При временно недоступном пути сохранять подтверждённые данные только если
  идентичность подтверждена. Недоступность creation time не трактовать как
  доказательство, что прежний экземпляр продолжает существовать.
- Повторы для неразрешённых metadata выполнять с ограниченной частотой;
  отказ не должен ни вызывать горячий цикл, ни навсегда запрещать уточнение.
- Проверить измерениями варианты получения свежей идентичности. Повторный вызов
  create_time на старом psutil.Process и oneshot не заменяют проверку PID reuse.
- Не удерживать неограниченное число handles; если выбран handle-подход,
  явно закрывать их при завершении, вытеснении и остановке.
- На этом этапе оставить интервалы 5/2/5 s для сопоставимого сравнения точности.

Проверки: PID reuse между обходами и во время чтения, исчезновение процесса,
AccessDenied, восстановление доступа, неизвестная identity, неполный обход,
общий resolver foreground/process. Проверять поведение, а не точное число
внутренних вызовов, если оно не является самим проверяемым ограничением.

Результат: отчёт до/после. Если стоимость свежей проверки остаётся высокой,
это основание для событийного источника, а не для отключения защиты identity.

## 3. Оптимизация подтверждённых затрат state manager и SQLite

Оценка от 2026-09-10: повторно разобран существующий light-профиль этапа 2
`build/benchmarks/20260909T182528Z-ea1fd998/01-light/performance.jsonl`.
Новые живые замеры для этой оценки не запускались. Текущий commit — `839b490`.
За 138,764 s внутреннего окна (с запуском/прогревом/остановкой) CPU процесса —
36,609 s. Доли ниже не смешиваются со внешним 120-секундным окном:

| Стадия | CPU time | Доля CPU процесса | Средний CPU, вся машина = 100% |
|---|---:|---:|---:|
| Process snapshot | 35,172 s | 96,07% | 1,584% |
| SQLite transaction, включая вложенную работу | 0,688 s | 1,88% | 0,031% |
| State copy | 0,016 s | 0,043% | 0,0007% |

SQLite connect/schema суммарно — 0,172 s CPU, около 0,0077 процентного пункта
среднего CPU машины. Эти вложенные измерения нельзя прибавлять к transaction.
Даже гипотетическое устранение всей измеренной стоимости transaction и state.copy
дало бы лишь около 0,032 процентного пункта; реальная оптимизация устранит часть.
Малые CPU-значения ограничены разрешением часов. Вывод относится к текущим
коротким фоновым сценариям, не к длительной работе с большой историей или UI.

Технических препятствий для этапа нет, но CPU-выгода сейчас мала. Изменения writer
и пропуска событий затрагивают владение потоком, timestamps, rollback/recovery.
Рекомендуется сначала отделить тяжёлую работу от оконного потока (этап 4), затем
подключить process events (этап 5). После этого повторно оценить state/SQLite,
включая сценарий частых process events. Код state/SQLite на этапе оценки не менялся.

Выполнять адресно по результатам этапов 1–2:

- Для часто читаемых flags/timestamps добавить компактное неизменяемое представление
  состояния; не копировать все карты процессов ради одного флага.
- Если значимы SQLite connect/schema, рассмотреть долговечное writer-подключение
  в потоке-владельце с проверкой схемы при открытии, корректным закрытием и recovery.
  Read-only API-подключения сохранить независимыми.
- Если значимы неизменные наблюдения, уменьшить избыточную обработку с сохранением
  last_event_at, границ idle и heartbeat. Нельзя просто пропускать все одинаковые
  события: их timestamp может участвовать в упорядочивании и восстановлении.
- Сохранить commit-before-publish, rollback, durability и единственного владельца
  runtime. Не уменьшать synchronous или частоту heartbeat ради красивой цифры CPU.

После каждого самостоятельного изменения — регрессия и повторный замер.

## 4. Очередь и отделение тяжёлой работы от оконного потока

Реализовано 2026-09-10. При переполнении используется recovery старого run на
последней подтверждённой границе и полный snapshot нового run: сверка текущего
состояния не выдаётся за восстановление потерянной истории. Интервалы polling
сохранены. Ниже — требования этапа; детали поведения описаны в [windows.md](windows.md).

- Перенести последовательную обработку коллектора/runtime в поток-владелец,
  где создаются SessionManager и writer-подключение; оконный поток передаёт сигналы.
- Не ограничиваться Thread вокруг snapshot: resolver, runtime и API-команды
  должны иметь согласованное владение и порядок доставки.
- Быстрые callbacks фиксируют необходимые поля и время события, ставят его
  в очередь; не читают metadata/icons и не обращаются к SQLite.
- Обеспечить ограниченную очередь, наблюдаемое переполнение и reconciliation
  после разрыва наблюдения. Lifecycle-события не объединять без разбора.
- Отдельно решить порядок process, foreground, power и heartbeat, буферизацию
  во время snapshot, поздние события и запрет применения устаревшего результата
  после нового sleep/lock. Простой FIFO из разных источников не гарантирует
  порядок по времени события; текущий manager отбрасывает старые timestamps.
- Измерить задержку message loop и очереди. Python worker сам по себе не
  гарантирует устранение задержек, если тяжёлая операция удерживает GIL.

Результат: отзывчивый tray и готовая инфраструктура источников событий.
Это этап снижения задержек; отдельного обещания снижения CPU у него нет.

## 5. События процессов и редкий reconciliation

- Первым сделать ограниченный прототип WMI Win32_ProcessStartTrace/StopTrace.
  Использовать trace events, а не intrinsic WMI-запрос с частым WITHIN polling.
- Проверить работу под обычным пользователем, задержки, короткие процессы,
  частые старты, отказ/переподключение WMI и нагрузку приложения + WmiPrvSE.
- При неудовлетворительном результате сравнить ETW; перед выбором проверить
  требования конкретной trace session к правам и поведению portable-сборки.
- Подписаться до начального snapshot, буферизовать события, затем свести снимок
  и события без двойного открытия/закрытия сессий. Не игнорировать все ранние
  события: короткий процесс мог целиком существовать во время snapshot.
- Для start разрешать только новый процесс, для stop закрывать нужный экземпляр.
  Поздний stop старого PID не должен закрывать новый процесс с тем же номером.
- При здоровой подписке перейти на reconciliation раз в 60 s; при обнаруженном
  сбое выполнить внеплановую сверку и временно вернуть оптимизированный poll 5 s.
- На wake/unlock сохранить свежую сверку и существующие правила границ состояния.
- События процессов продолжать принимать в IDLE и LOCKED.
- Раздельно учитывать исправление текущего состояния и потерю истории:
  reconciliation не восстанавливает точные границы пропущенного короткого процесса.

Результат: основная работа пропорциональна изменениям, а не общему числу процессов.

## 6. Foreground/title hooks

- SetWinEventHook: EVENT_SYSTEM_FOREGROUND и EVENT_OBJECT_NAMECHANGE;
  WINEVENT_OUTOFCONTEXT, фильтрация window/object, корректное снятие hooks.
- На foreground определять только владельца нужного окна; полный process snapshot
  не выполнять. Учитывать переключения внутри приложения и повторное использование HWND.
- Объединять только дубли без потери значимых переключений; измерять поток title events.
- Оставить fallback foreground/title poll, стартовый ориентир — 20 s,
  и свежую проверку после unlock/wake. При неработающем hook вернуть прежний poll.
- Оставить лёгкую проверку idle каждые 2 s. При отключённом сборе titles
  не читать заголовок для истории. Существующая семантика foreground в IDLE сохраняется.

Результат: более точные переключения и меньше лишних foreground-запросов;
основной эффект по CPU ожидается от предыдущих этапов.

## 7. Инкрементальное чтение Kernel-Power

- После начальной загрузки читать новые записи через bookmark/record cursor.
- Сохранять незавершённые пары modern/classic между чтениями и защиту от дублей.
- Обработать очистку/ротацию журнала, недействительный cursor и позднюю запись событий.
- Сохранить системный журнал источником границ Modern Standby; сообщения desktop
  не заменяют эти границы. Повторить сценарии из manual-retest-2026-09-08.md.

Этап можно перенести раньше, если baseline покажет заметный вклад power history.

## 8. Фильтр сбора процессов — отдельное изменение поведения

- Разделить текущий ignored для статистики и явное исключение из сбора.
- Сделать проверяемые правила по executable; не исключать весь C:\Windows,
  все Microsoft-приложения или все процессы без окна.
- Классифицировать экземпляр один раз и кешировать результат; продолжать
  минимальный учёт lifecycle/identity для удаления кеша и защиты от PID reuse.
- При изменении правил инвалидировать соответствующий кеш. Новые разрешённые
  сессии начинать с момента наблюдения, не восстанавливать вымышленную историю.
- Foreground исключённого приложения должен завершать foreground предыдущего.
- Измерить выгоду отдельно; не выдавать уменьшение полноты истории за ускорение
  при неизменной функциональности. По умолчанию сохранить нынешний охват сбора.

## 9. Итоговая проверка и критерии приёмки

Предварительные целевые показатели, которые предстоит подтвердить на этом ПК:

- Средний CPU приложения после прогрева в спокойных ACTIVE/IDLE сценариях — <1%
  всей 16-поточной системы; отдельный отчёт с UI открытым и закрытым.
- Вклад регулярной сверки процессов в CPU — минимум на 80% ниже baseline;
  дополнительно показать совокупную стоимость collector + event source.
- Прогретый snapshot: p95 <500 ms при сопоставимом числе процессов.
- Задержка обработки foreground при обычной нагрузке: p95 <250 ms;
  отдельно измерить межисточниковую очередь и системные lock/wake события.
- Отсутствие регулярных двухсекундных блокировок оконного потока, необъяснённого
  роста памяти/handles/очереди и потерь в контролируемом сценарии процессов.
- Незаметные накладные расходы отключённой диагностики; для включённой лёгкой
  диагностики показать абсолютную прибавку CPU и сопоставить её с шумом измерения.

Выполнить релевантные тесты на каждом этапе, полную регрессию и packaged smoke
перед итоговой сборкой. Затем длительный прогон 24 h с реальными idle/lock/sleep,
перезапуском и проверкой БД: целостность, непротиворечивые интервалы, отсутствие
двойных сессий и корректный recovery. Ручные действия, которые ещё не выполнены,
явно оставить в отчёте как непроверенные.

Для каждой версии сохранять таблицу: версия/сценарий, CPU seconds/min, CPU mean,
snapshot p95/max, event latency p95/max, память/handles, ошибки/потери,
изменения точности и вывод о сохранении изменения.

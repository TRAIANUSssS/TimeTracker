# Результат длительного сравнения polling и ETW

Источник: `build/process-events-benchmark/20260910T181842880096Z/report.json`.
Пользователь запустил collector-host в повышенном терминале и suite в обычном,
одновременно. Прогоны внутри suite выполнялись последовательно — это правильный порядок.

`passed=true`, `complete=true`: завершились проверка устойчивости и восемь прогонов
по 600 s после 30 s прогрева. Windows 11, Python 3.13.9, psutil 7.2.2, 16 логических CPU.
Commit `75e7c7a3623754c3240569668ae5dac9b5e15a5d`, рабочее дерево с изменениями;
SHA-256 исходников во всех прогонах:
`e1a046a6209819a87a8152d71142d14de6c9bf8528271b23464e510d0539e76d`.

## CPU

Сумма CPU worker с измерительным кодом и отдельного collector-host, взвешенная
по фактической длительности двух повторений на режим. Интерфейс/API/иконки,
запуск/прогрев/выход и CPU помощников нагрузки в эту сумму не входят.

| Сценарий | Polling, CPU s/min | ETW, CPU s/min | Polling, % машины | ETW, % машины | Наблюдаемое снижение |
|---|---:|---:|---:|---:|---:|
| Без контрольных запусков | 11,191 | 2,708 | 1,166% | 0,282% | 75,80% |
| Контрольные короткие процессы | 12,240 | 2,717 | 1,275% | 0,283% | 77,80% |

Это предварительная оценка эффекта, не принятый строгий итог A/B. Оба сравнения
имеют `comparable=false`: доля ACTIVE различалась более чем на 10 процентных пунктов.
Пороги проверки и исходный отчёт не изменялись после получения результата.

| Прогон | Режим | ACTIVE, % времени | CPU s/min, всё окно | Средний фон CPU системы |
|---|---|---:|---:|---:|
| quiet-1 | polling | 100,0% | 11,806 | 18,95% |
| quiet-2 | ETW | 84,1% | 2,623 | 20,06% |
| quiet-3 | ETW | 37,1% | 2,792 | 19,66% |
| quiet-4 | polling | 81,1% | 10,577 | 15,73% |
| churn-1 | polling | 83,1% | 11,144 | 16,73% |
| churn-2 | ETW | 100,0% | 2,752 | 18,59% |
| churn-3 | ETW | 100,0% | 2,683 | 18,78% |
| churn-4 | polling | 100,0% | 13,336 | 20,94% |

Если рассматривать только ACTIVE, в quiet получено 11,226 → 2,760 CPU s/min
(−75,41%), в churn — 12,442 → 2,717 (−78,16%). Это полезная проверка направления
эффекта, но она не устраняет различия фоновых процессов и распределения нагрузки.
Данных для двух повторений IDLE в каждом режиме нет. Для точного итогового процента
нужен сопоставимый контрольный сценарий; весь выполненный прогон от этого не теряет
ценности как проверка устойчивости и оценка порядка эффекта.

За каждое измеряемое окно полный список процессов читался 117–118 раз при polling
и 10 раз при ETW: примерно на 91,5% меньше вызовов. При этом отдельный snapshot не
стал быстрее: среднее время в ETW-прогонах 1,05–1,13 s, p95 1,18–1,39 s; целевой
snapshot p95 <500 ms не достигнут. Среднее число процессов в снимках 347–362.
CPU самого collector-host за 10 минут — 1,078–1,453 s, то есть около
0,011–0,015% всей машины, и уже включён в таблицу выше.

Профили `performance.jsonl` охватывают весь жизненный цикл каждого worker, включая
прогрев и завершение, поэтому их нельзя делить на CPU только измеряемого окна.
В ETW-профилях sqlite.transaction занимает 6,078–7,641 CPU s, state.copy —
0,078–0,219 CPU s. Это сохраняет основание отдельно проверить пакетные транзакции,
но ещё не показывает экономию от такой оптимизации. Вложенные стадии не суммируются
с родительскими.

## Устойчивость и точность

Проверка остановки и повторного подключения прошла: `fallback_snapshot=true`,
`reconnected=true`, два поколения источника, 12 из 12 контрольных процессов
с точными сессиями. Максимальное отклонение длительности — 1,191 ms.
Это штатная остановка/перезапуск ETW; аварийный обрыв проверен отдельно автотестами IPC.

Во всех четырёх ETW-замерах одно поколение на измеряемое окно, `faults=0`,
`invalid=false`, после завершения `pending=0`, `shutdown_complete=true`.
Максимальная очередь reader — 9–34 записи при ёмкости 4096; в отдельной проверке
устойчивости — 136. `healthy=false` в итоговой сводке ожидаем: источник уже остановлен.

ETW сохранил **120 из 120** помощников churn с погрешностью длительности ≤2 ms
(фактический максимум 1,415 ms при округлении вверх). Polling заметил **17 из 120**
(9 и 8 по повторам); ни один наблюдаемый polling-интервал не попал в допуск 2 ms.
Это ожидаемое ограничение polling 5 s для процессов с жизнью 0,3/2 s, а не ошибка БД.

Во всех девяти БД integrity=ok, ошибок foreign keys, открытых и отрицательных
интервалов нет; run закрыт нормально. Дополнительный read-only аудит не нашёл
сессий после конца run и положительных foreground-интервалов после завершения
связанного процесса. Во всех профилях отсутствуют ошибки manager/SQLite/collector.tick.

В ETW-прогонах handles worker менялись на −2…+1 между началом и концом окна,
handles сборщика сохранялись на 189. RSS worker вырос примерно на 1,5–3,2 MiB за
10 минут. Измеритель сам сохраняет выборки в RAM, поэтому рост нельзя автоматически
приписать утечке трекера; также он не доказывает её отсутствие. Проверка одного
долго живущего полного приложения по-прежнему нужна: здесь каждый worker новый.

## Статус

Контролируемая устойчивость и длительные окна worker проверены. Выигрыш ETW по CPU
и полноте коротких процессов выражен; точная величина CPU-экономии остаётся
предварительной из-за различий ACTIVE/IDLE. Весь этап 5 пока не закрыт: остаются
реальные sleep/wake/lock в полном приложении, непрерывный длительный прогон и
сопоставимое контрольное измерение для итогового процента. Команды ручного сценария
уже есть в [инструкции](process-events-benchmark.md#что-остаётся-ручным).

# Этап 2: кеш процессов — 2026-09-09

## Изменение

В `ProcessCollector` добавлен кеш неизменяемых `ProcessObservation` по PID
с обязательным сравнением creation time. Каждый проход и foreground-запрос
получают свежий `psutil.Process`; identity никогда не подтверждается старым
кешированным create_time переданного объекта.

Если identity совпала, возвращается сохранённое наблюдение без повторного exe,
metadata и второй проверки creation time. При новом или уточняемом наблюдении
повторная проверка остаётся и теперь выполняется после чтения metadata.
Смена PID-владельца или исчезновение за время чтения отбрасывают результат.

Успешный полный список удаляет отсутствующие записи кеша. Обнаруженное завершение
через foreground также удаляет запись. При полном отказе перечисления прежний
набор не подменяется пустым. Неизвестный creation time не позволяет использовать
положительный кеш: остаётся прежний continuity token, но путь читается заново.
Windows handles между опросами не удерживаются.

Для подтверждённого экземпляра неизвестный путь и неполные metadata повторно
разрешаются раз в 60 секунд по monotonic-часам. Лимит чтения metadata общий для
одного executable. Известные поля сохраняются при временной ошибке уточнения;
иконки не читаются повторно. Новый экземпляр с тем же PID сразу проходит новое
разрешение, не наследуя старый срок повтора.

Цена ограниченных повторов: восстановившийся доступ к ранее неизвестному пути
может быть замечен через 60 секунд плюс очередной poll и длительность сбора.
Существование процесса проверяется по-прежнему каждый цикл, даже пока его путь
остаётся неизвестным. Полные данные живого экземпляра кешируются до его завершения.

Интервалы process/foreground/heartbeat остались **5/2/5 секунд**. Событийный сбор,
блэклист, очереди и изменения SQLite в этот этап не входят.

## Почему ожидается примерно двукратное ускорение

Исходный профиль показал доминирование двух create_time. В установленном psutil
7.2.2 на Windows при отказе быстрого запроса времени процесса используется медленный
резервный путь (`_pswindows.Process.create_time` → `_proc_info`). Кеширование
устраняет вторую такую проверку для известного экземпляра, сохраняя первую свежей.
`oneshot` не используется как замена проверке identity, поскольку create_time
кешируется объектом: [документация psutil](https://psutil.readthedocs.io/stable/#psutil.Process.create_time).

## Короткие замеры до и после

Исходная версия — commit `3c61e29` (этап диагностики). Замер до изменения выполнен
в этой же сессии. После — тот же checkout с изменениями кеша. Windows 11 build
26200, Python 3.13.9, psutil 7.2.2, 16 логических процессоров.

Micro-прогон использует коллектор без SQLite и иконок, подробные таймеры включены:

| Показатель | До | После |
|---|---:|---:|
| Процессов | 357–360 | 351 |
| Первый snapshot, wall | 2,92 s | 2,75 s |
| Прогретый snapshot, wall | 2,66–3,00 s | 1,14–1,48 s |
| Прогретый snapshot, CPU | 2,55–2,84 s | 1,09–1,38 s |

Средний wall time прогретого snapshot: **2,832 → 1,302 s** (около **−54%**).
Средний CPU time: **2,695 → 1,219 s** (около **−55%**).
Выборки небольшие (2 прогретых snapshot до и 4 после), число процессов немного
различается; это оценка эффекта, не строгий статистический предел.

За пять snapshot после изменения зарегистрировано **351 cache miss** и
**1404 cache hit**. exe и повторный create_time запрашивались 351 раз вместо
потенциальных 1755. Первое чтение identity продолжало выполняться для каждого
наблюдения. Первый snapshot существенно не ускорился — кеш ещё пуст.

## CPU всего приложения

Непосредственно перед изменением выполнен off-прогон 60 s, после — off-прогон
120 s. В обоих случаях прогрев 15 s, ACTIVE, отдельная тестовая БД:

| Показатель | До | После |
|---|---:|---:|
| Средний CPU приложения (вся машина = 100%) | 3,097% | 1,606% |
| CPU seconds/minute | 29,73 | 15,41 |
| P95 секундных показаний CPU | 6,109% | 5,519% |
| Максимум секундного CPU | 6,220% | 6,011% |

Средняя нагрузка уменьшилась примерно на **48%**. Это короткое последовательное
сравнение при обычной работе ПК, без фиксации фоновой нагрузки; длительности окон
различаются. Пики остаются: snapshot по-прежнему выполняется каждые пять секунд.

После off-прогона: RSS 69,15 → 69,61 MB (десятичные), handles 253 → 244;
validation_passed=true, integrity_check=ok, foreign key ошибок нет, сессии закрыты,
отрицательных интервалов нет. Этот короткий прогон не заменяет проверку утечек 24 h.

В отдельном 120-секундном light-прогоне средний CPU — **1,622%**. Он захватил
92,8 s IDLE со средним CPU **1,576%**: отслеживание процессов в IDLE сохраняется.
Во внутреннем отчёте второй минутный интервал содержит 12 snapshot с p95 wall
**1,551 s**; последний короткий интервал — 3 snapshot с p95 **1,593 s**.
Первый интервал включает холодный старт и не используется как прогретый p95.
Глобальный p95 не вычислялся усреднением этих значений. Общий средний wall time
всех 27 snapshot (включая запуск) — 1,392 s.

В отдельной portable-сборке выполнен off-прогон 60 s после 15 s прогрева,
полностью в IDLE: **1,559% CPU**. Запуск завершился штатно, validation_passed=true,
handles 247 → 244. Сборка находится в
`build/process-cache-package/dist/TimeTracker/TimeTracker.exe` и не заменяет
ранее установленный/запущенный экземпляр пользователя.

## Проверка поведения

Полная регрессия после последнего изменения: **240 passed**, 2 opt-in live-теста
пропущены стандартным pytest. Добавлены сценарии кеширования и отказов доступа,
PID reuse во время exe/metadata, stale psutil-объекта, исчезновения процесса,
очистки кеша, отложенного повторного чтения и общей metadata нескольких процессов.

Живые проверки runner после изменения: два Python-прогона off/light по 120 s,
portable off 60 s и churn 60 s. Во всех тестовых БД integrity_check=ok,
нет нарушений foreign key, отрицательных интервалов и оставшихся открытых сессий;
все процессы трекера завершены штатно. Часовой протокол и ручные fullscreen,
lock/unlock, sleep/wake повторно не выполнялись.

Churn прошёл в IDLE: оба helper-процесса с sleep 7 s обнаружены и закрыты,
три с sleep 0,3 s пропущены, как и до кеширования. Средний CPU — **1,606%**.
Ускорение кеша не устраняет принципиальный пропуск коротких процессов между
poll; для этого необходим событийный источник. PID reuse проверен
детерминированными тестами, а не предположением, что Windows обязательно
переиспользует PID в коротком живом прогоне.

Цель всей программы оптимизации (<1% CPU и p95 snapshot <500 ms) не считается
достигнутой этим этапом: одна дорогая проверка identity на процесс всё ещё нужна.
Дальнейшее уменьшение частоты полных обходов требует этапа process events
с reconciliation либо отдельно проверенного более дешёвого источника identity.

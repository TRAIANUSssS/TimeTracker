# Устойчивость и сравнительный CPU process events

Инструмент: `tools/benchmark_process_events.py`. Он создаёт отдельный процесс worker
и новую SQLite для каждого прогона. Рабочая БД приложения не используется.
Результаты сохраняются в `build/process-events-benchmark/<timestamp>/`.

## Запуск длительной проверки

В повышенном PowerShell **того же пользователя** из корня проекта:

```powershell
cd E:\Projects\TimeTracker
.\.venv\Scripts\python.exe tools/benchmark_process_events.py --collector-host
```

Затем в обычном терминале VS Code:

```powershell
.\.venv\Scripts\python.exe tools/benchmark_process_events.py
```

Старый `run_etw_collector.py` для этой проверки не нужен. Новый host последовательно
обслужит шесть собственных ETW-сессий и завершится. Он использует отдельные каналы
`cpu-stability-*`, не устанавливает службу и не запускает команды по запросу клиента.
Существующая команда `finish` завершает только текущую принадлежащую ему сессию.
Доступ к пользовательским исходникам/пакетам повышенного Python — тот же, что у
предыдущего диагностического сборщика; автоматическая установка не добавлена.

Полный набор занимает около **85 минут**:

1. Сборщик работает 10 s, штатно прекращает поток, worker возвращается к polling.
   После паузы host создаёт новую ETW-сессию; проверяются новое поколение и подключение.
   Далее 20 s контролируемых коротких процессов и подтверждённое завершение worker.
2. Спокойный сценарий: polling → ETW → ETW → polling.
3. Сценарий запуска процессов: та же последовательность; раз в 10 s создаётся
   собственный невидимый помощник с жизнью попеременно 0,3 и 2 s.

Каждый из восьми замеров содержит 30 s прогрева и 600 s измерения. Внешние программы
и пользовательский ввод не генерируются. Для сопоставимости желательно оставить ПК
включённым, подключённым к питанию, с одинаковым набором приложений; не запускать
сборки/игры/обновления и не менять исходники во время сравнения. Сам инструмент
настройки питания и таймер сна не меняет. Сон/перевод часов более чем на 2 s либо
разрыв между выборками более 5 s делают результат не прошедшим проверку.

Параметры `--duration`, `--warmup`, `--scenarios` и `--channel` должны совпадать в обоих
терминалах. Например, для короткой проверки инструмента можно передать обоим
`--duration 20 --warmup 5 --scenarios quiet`. Такой прогон не заменяет длительный замер.
Если набор прервался, завершить ожидающий host через Ctrl+C и запустить обе команды
заново: новая попытка получит отдельную папку. Отчёты уже завершённых прогонов сохраняются.

## Что именно измеряется

- CPU процесса worker **вместе с его лёгким измерительным кодом** и отдельно CPU
  повышенного collector-host. Используются разности накопительных счётчиков по одному
  измеряемому окну, результат — CPU seconds/min и процент всей машины.
- Сборщик учитывается через сохранённый `PROCESS_QUERY_LIMITED_INFORMATION` handle
  и GetProcessTimes. Его завершение внутри измеряемого окна — ошибка, PID reuse
  не перенаправляет измерение. Недоступность CPU не подменяется нулём.
- RSS/handles worker, доступные RSS/handles сборщика, максимальная длина очереди reader,
  количество принятых событий и ошибок, поколение/здоровье источника.
- Время и размер каждого полного snapshot; полные профили `performance.jsonl` для
  разбора SQLite, state и прочих стадий. Лёгкая диагностика одинакова в обоих режимах.
- Фактические ACTIVE/IDLE/LOCKED и переходы между ними, общий фон CPU системы.
  Состояния наблюдаются, а не принудительно задаются. Если ПК всё время в IDLE,
  результат ничего не доказывает про длительный ACTIVE.
- Точность собственных коротких процессов по GetProcessTimes. Для ETW нужны ровно
  одна сессия с известным executable и отклонение длительности не более 2 ms.
  Polling может пропустить короткий процесс; это показывается в отчёте, но не считается
  ошибкой инструмента. Таким образом учитывается и разница полноты собираемых данных.

Это сравнение пути сбора **без UI, API, иконок и оконной очереди приложения**.
CPU помощников нагрузки и родительского launcher не входит в сумму worker + collector.
Запуск, прогрев и shutdown находятся вне основного измерения; расходы logman на
создание/остановку сессии также вне него. Системные расходы ETW не выделены из общего
CPU Windows. Этот отчёт нельзя называть измерением всего приложения с открытым UI.
Память и handles сохраняются как временные ряды для проверки роста, но положительная
разность сама по себе не объявляется утечкой или доказательством её отсутствия.

## Проверки и выводы

Для каждого прогона: `samples.jsonl`, `performance.jsonl`, `tracker.db`, `report.json`.
В корне: `environment.json` (версии/commit), `configuration.json` (параметры и SHA-256
исходников), общий `report.json`, при ошибке — `failure.json`.
Сводки и samples не содержат путей чужих процессов или заголовков окон; SQLite
содержит обычную локальную историю тестового worker.

`passed` означает прохождение функциональных проверок: worker жив во время замера,
ETW непрерывен в измеряемом окне, final delivery подтверждена, SQLite цела,
нет открытых/отрицательных сессий, единственный run закрыт нормально.
`complete=true` означает окончание всех девяти прогонов, включая устойчивость.

`comparisons` содержит расчёт по каждому сценарию и общим состояниям. При провале
прогона сравнение не рассчитывается. Разница фоновой нагрузки или доли ACTIVE более
10 процентных пунктов и разное число контрольных процессов помечают сравнение как
несопоставимое, сохраняя исходные числа для разбора. Это диагностические пороги,
не статистические доверительные интервалы; два повторения на режим недостаточны
для вывода об очень маленьком улучшении. Неизменность исходников проверяется между
прогонами и после каждого дочернего запуска.

Автоматические тесты `tests/test_event_benchmark.py` уже проверяют настоящие Windows
pipe/worker/SQLite при внезапном обрыве, пропуске sequence и переполнении reader:
переход на polling, новое поколение, восстановление и закрытие истории. Отдельный
тест выполняет ETW-ветку самого измерителя с искусственным источником и desktop.
Он проверяет инструменты, а не производительность ETW. Реальная проверка host выше
использует штатную остановку сессии и повторный запуск; аварийное убийство повышенного
процесса в неё не входит.

Локально выполнен минутный polling/churn smoke с отдельной БД:
`build/process-events-benchmark/local-polling-smoke-20260910/report.json`, passed=true.
Это проверка ранней версии инструмента при параллельных автотестах; её CPU нельзя
использовать как итоговый baseline. Полный набор на момент проверки: 340 passed,
2 opt-in skipped; после добавления проверки runner отдельно прошли все 7 новых тестов.
Длительный набор выполнен пользователем: `20260910T181842880096Z`, passed=true,
complete=true. Устойчивость и девять БД прошли проверку; наблюдаемая CPU-экономия
около 76–78%, но сравнения помечены comparable=false из-за различий ACTIVE/IDLE.
[Разбор результатов и ограничений](performance-etw-abba-2026-09-10.md).

## Что остаётся ручным

Во время CPU-сравнения клики не нужны. Реальные сон/пробуждение, блокировка и
длительная повседневная работа проверяются отдельным прогоном полного приложения;
они не подмешиваются в ABBA. Этот набор не заменяет запланированный непрерывный
24-часовой прогон приложения и проверку UI/оконной очереди. Эти пункты остаются
непроверенными до отдельных результатов.

После ABBA для часовой проверки полного приложения в повышенном терминале:

```powershell
.\.venv\Scripts\python.exe tools/run_etw_collector.py --channel stability-soak --seconds 7200
```

В течение 30 секунд в обычном терминале:

```powershell
.\.venv\Scripts\python.exe tools/benchmark_tracker.py --duration 3600 --warmup 30 --repeats 1 --modes light --process-events stability-soak --probe-window
```

Этот runner использует настоящий оконный цикл приложения, API и отдельную БД.
В течение часа пользователь может поработать обычно, заблокировать/разблокировать ПК,
перевести его в сон и пробудить. Для проверки границ полезно записать приблизительное
время этих действий. Runner сам завершит приложение; после команды finish завершится
и сборщик. Отчёт — новая папка в `build/benchmarks/`. Его CPU не используется в ABBA:
сценарий включает сон и не учитывает внешний сборщик в своей сумме. Не запускать эту
проверку одновременно с CPU-сравнением. Автоматический аудит БД и профиля необходимо
дополнить проверкой реальных границ сна/блокировки по полученному отчёту.

Основания: [GetProcessTimes и права handle](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes),
[QueryUnbiasedInterruptTime исключает сон](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime).

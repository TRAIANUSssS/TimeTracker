# Первый baseline CPU — 2026-09-09

Оптимизации коллектора ещё не применялись. Добавлены внутренние таймеры,
внешний runner и генератор отчётов. Пользовательская БД в замерах не использовалась.

## Методика и пределы

Windows 11 build 26200, 16 логических процессоров, Python 3.13.9, psutil 7.2.2.
Checkout: `8352d8715407b517593ed9114a459fd9b27fcd1b` с незакоммиченными изменениями
диагностики. Измерялся фактический рабочий PID; промежуточный Windows venv launcher
не включался вместо приложения.

Выполнен быстрый baseline: три пары off/light, по 120 секунд измерения после
15 секунд прогрева; порядок off/light, light/off, off/light. Запуск/прогрев/остановка
отделены от внешнего steady-state окна. ПК оставался в обычном использовании;
режимы ACTIVE/IDLE наблюдались, ввод не имитировался. Это предварительная рабочая
база сравнения, а не полный протокол 3 × 10 минут на каждый режим.

`off` отключает внутренние таймеры в текущей версии кода. Сравнение off/light
не измеряет стоимость отключённых обёрток относительно предыдущего checkout.
Большие сборки и полная регрессия выполнялись после серии; во время серии
редактировалась документация и запускались короткие проверки инструментов.

## CPU всего приложения

| Прогон | Таймеры | CPU приложения (вся машина = 100%) | CPU seconds/minute |
|---|---|---:|---:|
| 1 | off | 2,901% | 27,85 |
| 1 | light | 2,774% | 26,63 |
| 2 | light | 3,092% | 29,68 |
| 2 | off | 2,928% | 28,11 |
| 3 | off | 2,847% | 27,34 |
| 3 | light | 2,937% | 28,20 |

Взвешенные средние: **2,892% off** и **2,934% light**. Разница — **0,042 процентного
пункта** (около 1,45% относительно off). Она меньше разброса отдельных прогонов;
вывод о точной величине overhead по этой короткой серии делать нельзя.

P95 секундных показаний CPU: около 6,10–6,20%; максимум: около 6,32%.
В этом измерении 6% характеризуют пики, а не среднюю нагрузку.

В третьем off-прогоне было 94,7 s IDLE с CPU **2,887%**. Остальные длительные
участки — преимущественно ACTIVE. Это подтверждает, что текущий process polling
продолжает расходовать CPU при отсутствии пользовательского ввода.

RSS в конце прогонов: примерно 65,9–66,7 MiB. Число handles не росло:
в каждом прогоне в конце на 9 меньше, чем в начале измерительного окна.
Длительность недостаточна для вывода об отсутствии долгосрочных утечек.

## Что потребляет CPU

Во внутренних light-отчётах (включая startup/warmup/shutdown):

- Полный process snapshot: **97,81–97,89% CPU-времени всего процесса**.
- Средний wall time snapshot по трём прогонам: **2,32–2,63 s**; максимум **3,41 s**.
- Неатрибутированный остаток CPU: около 0,69–0,77 s за прогон, примерно 1–1,2%
  CPU-времени процесса. Он включает другие потоки, диагностику и разрешение часов.
- В первом light-прогоне SQLite transaction суммарно потребовал около 500 ms CPU,
  копирование state — 31 ms. Это существенно меньше 59,9 s CPU на process snapshot.
- Kernel-Power в первом light-прогоне: около 21,5 ms wall time на чтение,
  суммарно 15,6 ms CPU. Основной эффект здесь — ожидание, не CPU.

Вложенные inclusive стадии не суммировались. Окна внутренних и внешних измерений
различаются; абсолютные CPU totals между ними напрямую не вычитались.

Отдельный micro-прогон без БД и иконок: 347/346/346 процессов.
Первый snapshot: 6,43 s wall / 2,30 s CPU; прогретые: 2,21/2,25 s wall и
2,19/2,13 s CPU. Холодный кеш — кеш metadata процесса; кеш Windows не очищался.

Из 6,61 s CPU трёх snapshot **6,08 s (около 92%)** пришлись на первое и повторное
чтение creation time. Получение exe — около 156 ms CPU, metadata — около 125 ms CPU.
При первом чтении metadata было около 4,2 s ожидания, поэтому startup нужно
рассматривать отдельно от прогретого режима.

## Решение по следующему этапу

Первым оптимизировать `ProcessCollector`, особенно получение и свежую проверку
identity. Простое кеширование exe даст ограниченный эффект: доминируют creation time.
Защиту от PID reuse сохранить. После изменения повторить этот же runner.

Переделка SQLite и state manager ради CPU по текущему baseline не приоритетна.
Профилировать их дальше имеет смысл, если после ускорения коллектора их доля
станет значимой. Foreground hooks полезны для точности, но почти не влияют
на найденную основную нагрузку.

## Проверки

Собрана отдельная portable-копия в `build/performance-package/dist/TimeTracker`.
На ней выполнена одна пара по 60 s после 15 s прогрева: **2,772% off** и
**2,612% light**, пики около 6,3%. Оба запуска прошли проверку БД и штатно
завершились; JSONL внутренних стадий успешно записан из frozen exe.
Одна короткая пара не доказывает ускорения от диагностики: разница отражает
разброс и положение snapshot относительно измерительного окна.

Автоматический churn-сценарий, 60 s: пять helper-процессов без видимых окон.
Три процесса с заданным sleep 0,3 s не обнаружены, оба с sleep 7 s обнаружены.
У длинных процессов задержка первого наблюдения от creation time составила
около 6,2–6,5 s: к периоду polling добавляется длительность сбора snapshot.
Это исходное поведение коллектора, зафиксированное для сравнения с process events.
Средний CPU приложения в этом сценарии — 3,035%; тестовая БД прошла проверки.

Все шесть тестовых запусков завершились штатно. В каждой БД integrity_check=ok,
нет нарушений foreign key, открытых сессий после выхода и отрицательных интервалов.
Полная регрессия: 225 passed, 2 opt-in live-теста пропущены стандартным запуском.
Живой сбор и штатное завершение дополнительно проверены самим runner.

Полный часовой протокол, длительная проверка 24 h, реальные fullscreen и
sleep/wake в этой серии не выполнялись. Команды и ручной сценарий:
[performance.md](performance.md).

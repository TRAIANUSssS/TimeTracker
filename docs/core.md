# Ядро сессий

Этап 2 реализует обработку нормализованных наблюдений и жизненный цикл tracker.
Windows polling, доставка системных уведомлений, планировщик heartbeat и трей
подключаются на этапе 3. Запуск CLI пока только выводит статус или создаёт схему.

## Модули и владение состоянием

- `domain/events.py`: неизменяемые события, process identity и snapshots.
- `domain/system_state.py`: флаги и приоритет `SLEEP > LOCKED > IDLE > ACTIVE`.
- `domain/tracker_state.py`: процессы, счётчики приложений, открытые сессии и кеши в RAM.
- `domain/session_manager.py`: обработка события и восстановление истории.
- `domain/ports.py`: интерфейсы хранения, часов и поставщика полного snapshot.
- `storage/tracker_store.py`: адаптер этих интерфейсов к SQLite.
- `runtime.py`: блокировка, инициализация, старт, heartbeat и остановка.

Менеджер принадлежит одному потоку. Все наблюдения, heartbeat и будущие команды API
нужно последовательно передавать этому потоку. Чтение статистики использует отдельное
read-only подключение. Прямое изменение репозиториев во время работы менеджера
обходит его кеши и поэтому не является интерфейсом изменения runtime state.

Каждое событие обрабатывается на копии RAM-состояния внутри одной транзакции.
После успешного commit копия становится текущим состоянием; ошибка оставляет БД
и RAM без частичного перехода. Свойство `state` также возвращает отдельную копию.
Смена сессий атомарно продвигает `last_persisted_at`; heartbeat обновляет своё поле.
Чтение записи run после события синхронизирует эти служебные границы, а решения
о текущих процессах, foreground и running принимаются по RAM.

## Контракт наблюдений для Windows-адаптеров

Все времена — целые UTC Unix milliseconds. `observed_at` обозначает время получения
наблюдения, а не время его доставки в очередь. События нужно доставлять в порядке
наблюдения; heartbeat — после уже полученных событий. Менеджер отвергает наблюдения
старше последнего принятого события, чтобы поздний process poll не отменял новый foreground.
Он не сортирует очередь и не исправляет пропущенные Windows-уведомления.

`ProcessIdentity` состоит из PID и creation time. Если creation time недоступен,
адаптер выдаёт `observation_token`, общий для непрерывного наблюдения этого процесса
в foreground/process polling. После разрыва наблюдения требуется новый token.
Недоступность metadata при подтверждённой identity не означает завершения процесса.

`ProcessesObserved(complete=True)` — полный успешно полученный список PID.
Отсутствующие процессы закрываются на `observed_at`. Неполный список передаётся
с `complete=False`, при полном отказе poll событие можно пропустить. Ошибку всего
poll нельзя превращать в пустой полный список. Повторяющиеся PID в одном snapshot
отклоняются как ошибка нормализации. Счётчики сводятся после всего списка:
замена одного процесса другим у того же приложения не разрывает running session.

`ForegroundChanged` сначала регистрирует процесс и running тем же timestamp.
Неизменные application/executable/HWND/title не создают записей. Значение `None`
закрывает прежний foreground; последующее наблюдение не заполняет пропуск назад.
Неизвестный путь процесса сохраняется с `executable_id=NULL` без фиктивного приложения.
Подтверждённые PID и creation time разрешают уточнить executable старой process session;
running начинается только в момент определения приложения. Без creation time
уточнение закрывает старую process session и открывает новую.

`TrackerSnapshot` содержит согласованный полный список процессов, текущий foreground,
last input и флаги lock/sleep. Он нужен при запуске, `SystemWake` и `SessionUnlocked`;
timestamp snapshot должен совпадать с событием. Foreground может дополнить список
процессом, обнаруженным непосредственно при чтении окна. Для повторных обычных poll
используются `ProcessesObserved` и `ForegroundChanged`.

## Системные состояния и настройки

`IdleObserved` вычисляет порог в 300 000 ms. `IdleStarted` и `IdleEnded` дополнительно
проверяют соответствие заявленного перехода данным last input. Начало IDLE при переходе
из ACTIVE — `max(last_input_at + threshold, current_system_session.started_at)`:
оно может предшествовать времени обнаружения, но не пересекает запуск или предыдущее
системное состояние. Выход из IDLE записывается в момент наблюдения свежего ввода.
Foreground и running во время IDLE продолжаются.

Блокировка и сон закрывают текущий foreground. Process/running остаются открытыми;
во сне обычные process/foreground события не применяются. Unlock/wake заново вычисляют
состояние и перечитывают процессы и окно, поэтому старое окно не получает время после
возврата без подтверждения. Статистический слой этапа 4 исключит SLEEP из «Запущено»
пересечением running с ACTIVE/IDLE/LOCKED. Длительность сырой running session сама
по себе ещё не является значением колонки.

`ApplicationSettingsChanged` одновременно изменяет настройки БД и RAM. `ignored`
сохраняет исходную историю; фильтрация появится в статистике. Смена `track_titles`
перекрывает текущий foreground в момент команды, сохраняя старые titles.
При выключении title нормализуется в NULL ещё до сравнения наблюдений. При включении
новая сессия сначала имеет NULL, затем получает title из следующего свежего poll.

## Запуск, завершение и восстановление

Рабочая точка входа для будущего приложения — `TrackerRuntime(database, provider, clock=...)`.
`provider` реализует `snapshot() -> TrackerSnapshot`; часы — `now_ms() -> int`.
Часы по умолчанию используют системное UTC-время. Методы:

1. `start()` получает блокировку, инициализирует схему, читает snapshot и запускает менеджер.
2. `handle(event)` передаёт обычное наблюдение или команду настроек.
3. `heartbeat()` сохраняет подтверждённую границу; частоту задаёт будущий планировщик.
4. `stop()` закрывает все сессии и run одним timestamp с `exit_reason='normal'`.

Runtime также поддерживает `with`: штатный выход вызывает `stop()`, исключение — `abort()`.
`abort()` освобождает ресурсы, оставляя незакрытую историю для recovery. Ошибка записи
при `stop()` также оставляет run незавершённым и освобождает блокировку.
Lifecycle-события доступны напрямую в `SessionManager` для тестов, но через runtime
следует пользоваться `start()`/`stop()`, чтобы правильно управлять блокировкой.

Восстановление и новый старт составляют одну транзакцию. У незакрытого run граница —
`max(last_heartbeat_at, last_persisted_at)`. Все открытые process/running/foreground/system
сессии закрываются на этой границе, run получает `exit_reason='crash'`. Новый run
начинается на timestamp свежего snapshot; пропуск между ними остаётся без данных.
Если восстановление или запись стартового snapshot не удалась, откатывается вся операция.

При переводе часов назад устаревшие наблюдения отбрасываются; heartbeat и shutdown
ограничиваются снизу временем последнего принятого события. Запуск раньше последней
подтверждённой границы истории отклоняется через `ClockOrderError`. Это сохраняет
неотрицательные интервалы; коррекция системных часов и доставка уведомлений относятся
к интеграционному слою.

Блокировка хранится рядом с БД в `<имя файла>.lock`, берётся до инициализации/recovery
и удерживается на протяжении жизни runtime. Она привязана к каноническому пути БД;
одну историю следует открывать по одному пути. На Windows используется
[`msvcrt.locking`](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking),
на других ОС — [`fcntl.flock`](https://docs.python.org/3/library/fcntl.html#fcntl.flock).
ОС освобождает блокировку при гибели процесса. Сам файл не удаляется: его наличие
не означает работающий tracker. CLI `--init-db` соблюдает ту же блокировку.

Проверки описаны в [tests/README.md](../tests/README.md); настоящие Windows collectors
и расчёты статистики в этот этап не входят.

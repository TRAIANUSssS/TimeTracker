# Сбор активности Windows

Этап 3 подключает ядро к Windows 10/11. Запуск: `python -m time_tracker --track`,
без консоли — `time-tracker-tray.exe`. Оба варианта поддерживают `--database PATH`.
Права администратора для обычного запуска не требуются. Недоступные системные
и elevated процессы сохраняются с доступной частью metadata.

## Поток обработки

`application.py` собирает `WindowsAPI`, `WindowsProvider`, `TrackerRuntime`,
`CollectionController` и `TrayApplication`. Скрытое окно верхнего уровня принимает
сообщения Windows. Владелец окна одновременно является единственным владельцем
session manager и SQLite writer. `WM_TIMER` с периодом 250 ms проверяет сроки задач;
частоты foreground/idle — 2 s, процессов/heartbeat — 5 s. Это целевые интервалы:
медленный Windows API или первое чтение metadata могут задержать текущий цикл.

Расписание использует `time.monotonic()`, история — UTC milliseconds. Timestamp
берётся после чтения соответствующего источника. Heartbeat отправляется после
наблюдений цикла. При переводе UTC-часов назад старые события отбрасываются по
правилам ядра; сбор возобновится, когда часы достигнут последней принятой границы.

Вложенные уведомления Windows откладываются до завершения текущего обработчика;
выход во время обработки также ждёт её окончания. Нативные callbacks перехватывают
ошибки явно: неожиданная ошибка записи/обработки прекращает сбор, освобождает lock
и оставляет run для crash recovery. Исключение не остаётся незаметно внутри pywin32.

## Источники и отказ доступа

`ProcessCollector` очищает кеш `psutil.process_iter()` перед каждым полным списком:
современный psutil сам не проверяет PID reuse в кеше итератора. Creation time читается
из свежего объекта; перед использованием найденного пути identity проверяется ещё раз.
Foreground и process polling используют один resolver и общие continuity tokens.
После исчезновения PID token удаляется. Если creation time перестал быть доступен,
новое неизвестное наблюдение не заимствует прежнюю доказанную identity.

Отказ доступа к пути не равен завершению процесса. Известная identity с недоступным
путём позволяет ядру сохранить прежнюю связь. Невалидный/device path передаётся как
неизвестный. Ошибка всего перечисления не превращается в пустой список: текущие
процессы остаются до следующего успешного poll. Это может увеличить погрешность
running при длительном отказе источника, поэтому отказ записывается в журнал.

Foreground читается через `GetForegroundWindow`, `GetWindowThreadProcessId` и
`GetWindowText`. После разрешения metadata повторно проверяются HWND и владелец.
Недостоверное окно, исчезнувший процесс или ошибка Win32 дают пустой foreground;
ядро закрывает прежний интервал. FileDescription/ProductName извлекаются из
version resources один раз за запуск для каждого нормализованного пути.

`GetLastInputInfo` сопоставляется с `GetTickCount64`; unsigned-разность учитывает
32-битное переполнение tick count примерно раз в 49,7 суток. Это источник ввода
текущей пользовательской Windows-сессии. В MVP просмотр видео без ввода продолжает
приводить к IDLE по порогу ТЗ.

## Блокировка и сон

Окно регистрируется через `WTSRegisterSessionNotification` для текущей сессии.
Lock/unlock и отключение/подключение console/RDP доставляются через
`WM_WTSSESSION_CHANGE`. При запуске, возврате и регулярном опросе запрашивается
`WTSSessionInfoEx`: SessionFlags определяет блокировку, отключённая сессия также
не считается ACTIVE. Неизвестное состояние при старте отклоняет запуск.

Перед запуском сбора окно явно подписывается через `RegisterSuspendResumeNotification`.
Это обязательно для уведомлений DAM/Modern Standby (S0): одного обработчика
`WM_POWERBROADCAST` недостаточно. Ошибка подписки отклоняет запуск; при выходе
вызывается `UnregisterSuspendResumeNotification`. Факт подписки и полученные
sleep/wake/lock/unlock уведомления записываются в INFO для диагностики.

Источник границ выбирается по флагу `AoAc` из `GetPwrCapabilities`:

- На обычных S3-системах `WM_POWERBROADCAST/PBT_APMSUSPEND` открывает SLEEP.
  При resume сначала читаются только lock/idle, чтобы закончить сон без ожидания metadata.
- На системах Modern Standby (S0) уведомления DAM используются для приостановки
  polling и закрытия foreground. Точные завершённые интервалы берутся из журнала
  `System`, provider `Microsoft-Windows-Kernel-Power`: пары 506/507 для Modern Standby,
  42/107 для обычного сна/гибернации. Время — `TimeCreated.SystemTime`, с точностью
  хранения до миллисекунды. Короткий выход и повторный вход сохраняются отдельно.

`PowerHistory` читает события только начиная с текущего run: каждые 2 s, при resume
и перед выходом. Во время ожидания resume выполняются дополнительные чтения.
Незавершённая пара удерживает паузу; повторные чтения не дублируют уже применённые пары.
Отказ чтения журнала при запуске или работе останавливает сбор с явной ошибкой,
вместо незаметного перехода к менее точному источнику. Классический режим выбран
только при отсутствии AoAc, а не по наличию старых записей в журнале.

В S0 граница SLEEP не зависит от окончания полного snapshot. После получения пары
ядро атомарно заменяет пересекающуюся часть ACTIVE/IDLE/LOCKED на SLEEP. Состояния
до и после сохраняются. Пересекающий сон foreground обрезается или удаляется;
его хвост после пробуждения не дорисовывается. Свежие окна, наблюдавшиеся после
конца сна, сохраняются. Коррекция ограничена текущим незакрытым run, обновляет RAM
и `last_persisted_at` в одной транзакции. Старые завершённые запуски не меняются.
Смежные SLEEP-строки могут остаться отдельными, их интервалы не перекрываются.

До доставки полной пары записанное системное состояние является предварительным:
collector уже приостановлен, но SLEEP появится только после подтверждения обеих границ.
Если журнал был очищен, Windows не записала парное событие или приложение аварийно
завершилось до его получения, точный интервал из этих данных восстановить нельзя.
Обычное recovery ограничивает историю последней подтверждённой границей; импорт
поздних событий в уже закрытые запуски в этот механизм не входит.

После unlock/wake быстрый `user_snapshot` обновляет lock/idle отдельно от полного
перечисления процессов и окна. Unlock, пришедший раньше обновления WTS flags,
ждёт подтверждения. Если полный snapshot недоступен, он перечитывается до продолжения
polling; старый foreground не восстанавливается. Снимок, полученный до ещё одного
подтверждённого сна, отбрасывается. Ошибка регулярного чтения состояния пользователя
прекращает сбор с recovery при следующем запуске.

В журнале видны `Sleep boundary source: Kernel-Power` и отдельные строки
`Confirmed Kernel-Power sleep <start>..<end> (<duration> ms)` для проверки границ.

Сырые process/running интервалы могут проходить через сон. Вычитание SLEEP из колонки
«Запущено» выполняется пересечениями в статистическом слое этапа 4.

## Трей, журнал и иконки

Трей использует `Shell_NotifyIcon` и собственный значок розовых часов
(при отсутствии файла — стандартный значок Windows).
Сообщение `TaskbarCreated` восстанавливает значок после перезапуска Explorer.
Левый щелчок открывает dashboard, правый — меню. Меню содержит открытие dashboard,
переключатель автозапуска и недоступную паузу согласно MVP stub;
«Выход» закрывает сессии/run штатно. `WM_ENDSESSION` также завершает запись,
а отменённый `WM_QUERYENDSESSION` сам по себе её не останавливает.

Журнал — `logs/tracker.log` рядом с БД: до 2 MB на файл и три архивных файла.
INFO содержит lifecycle, переходы состояния и ID новых приложений; titles в него
не записываются. GUI entry point показывает сообщение при ошибке, консольный
возвращает ненулевой код завершения.

`IconCache` извлекает HICON из executable через `ExtractIconEx` и сохраняет PNG 32×32
в `icons/<sha256(normalized_path)>.png` рядом с БД. Иконки не хранятся в SQLite.
Графические handles освобождаются, файл заменяется атомарно. Существующий кеш
переиспользуется после перезапуска; версия рендеринга хранится в PNG metadata.
Кеш старой версии пересоздаётся из executable при следующем обращении.
Порядок строк нативного bitmap проверяется тестовым рисунком с разными верхом и низом.
Ошибка извлечения повторно не проверяется до
следующего запуска. Отсутствие ресурса или ошибка записи кеша не прерывает tracker.
API сможет найти иконку через `icon_key(executable.path)` либо показать fallback.

## Проверка на рабочем компьютере

Автоматические тесты покрывают fake sources, настоящий message loop с синтетическими
WTS/power сообщениями и отдельный короткий live smoke. Команды — в
[tests/README.md](../tests/README.md). Реальная блокировка экрана, suspend/hibernate,
смена пользователя/RDP и завершение Windows требуют ручной интеграционной проверки;
автотесты не выполняют эти действия над рабочей сессией.

Для ручной проверки запустите tracker с отдельной БД, переключите несколько окон,
заблокируйте и разблокируйте Windows, выполните сон/пробуждение и выйдите через трей.
Проверьте последовательность `system_state_sessions`, разрыв foreground на lock/sleep
и `exit_reason='normal'` у завершённого run. До появления API SQLite содержит сырую
историю. Итоги длительности и dashboard доступны в API и UI этапов 4–5.

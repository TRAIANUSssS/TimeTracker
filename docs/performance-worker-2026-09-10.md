# Этап 4: отдельный поток сбора и очередь уведомлений

Дата: 2026-09-10. Реализованы `CollectionWorker`, асинхронный старт/выход трея,
ограниченная очередь Windows-уведомлений, защита публикации наблюдений и доставка
настроек API единственному владельцу runtime/SQLite. Интервалы polling 5/2/5 секунд,
durability SQLite и охват процессов сохранены. WMI/ETW и редкая сверка — этап 5.

## Изменение поведения

- Окно Windows принимает сообщения, пока worker читает процессы, metadata, иконки
  или выполняет запись. SessionManager создаётся и используется только worker.
- Sleep/lock, пришедшие во время снимка, отменяют его публикацию. Очередь обрабатывается
  с callback timestamps. Wake/unlock в классическом режиме фиксируют границу отдельно
  от свежего user/process snapshot. Modern Standby сохраняет Kernel-Power как источник сна.
- Сигналы во время начального снимка заставляют повторить его; история начинается
  с непрерванного baseline. Уведомления работающего run не объединяются.
- Ёмкость очереди — 256. Переполнение логируется и вызывает recovery старого run
  на подтверждённой границе, затем новый run с полной сверкой. Потерянная история
  не восстанавливается вымышленными интервалами. Stop не зависит от свободного места.
- SQLite остаётся последовательным, commit-before-publish. Уже принятая запись
  завершается, при ошибке незакрытый run остаётся для recovery; ожидающие PATCH
  получают отказ. При конечном WM_ENDSESSION запись заканчивается до возврата ОС.

Подробности: [windows.md](windows.md), [performance.md](performance.md),
[контракт событий](core.md).

## Измерения

Windows 11, Python 3.13.9, psutil 7.2.2, 16 логических CPU. Portable one-directory
сборки: предыдущая диагностическая после кеширования и новая из текущих исходников.
Новая сборка: `build/worker-package/dist/TimeTracker/TimeTracker.exe`.
Измерения последовательные, новые тестовые БД/порты, без сборки и тестов в фоне.
Внешнее окно каждого прогона — 120 s, прогрев — 10 s, сценарий quiet.
WM_NULL round trip измеряется примерно раз в секунду с timeout 3000 ms.
Все приведённые прогоны размечены как ACTIVE; ручной ввод не имитировался.

| Сборка | Режим | Процессов на старте | CPU всей машины | RTT p95 | RTT max | Проб / отказов |
|---|---|---:|---:|---:|---:|---:|
| До | off | 333 | 1,139% | 369,84 ms | 1215,29 ms | 114 / 0 |
| После | off | 351 | 1,397% | 18,98 ms | 23,99 ms | 120 / 0 |
| После | light | 341 | 1,295% | 22,31 ms | 47,51 ms | 120 / 0 |
| До, повтор после новой сборки | light | 352 | 1,290% | 943,89 ms | 1157,56 ms | 108 / 0 |

В первом сравнении off/off p95 RTT уменьшился примерно в 19 раз. Длительные
задержки окна, связанные со snapshot, в новых коротких прогонах не наблюдались.
Это результат для отклика окна, а не гарантия времени доставки каждого события
в SQLite: очередь может ждать окончания текущего системного вызова.

Первый off/off показал рост CPU на 0,258 процентного пункта при изменившемся
числе процессов. Поэтому после новой версии повторно измерена старая сборка.
В повторном сравнении light/light CPU практически совпал: 1,290% до и 1,295%
после. Стоимость прогретого snapshot также сопоставима: mean второго внутреннего
интервала 1,093 s до и 1,031 s после. Устойчивого роста CPU от нового worker эти
короткие данные не показали, но и снижение CPU не доказали. Они не заменяют
чередующиеся десятиминутные повторы при сопоставимой фоновой нагрузке. Разницу
off/light также нельзя выдавать за измеренную стоимость диагностики.

Повторная старая сборка снова имела задержки окна до 1,16 s при сопоставимом CPU:
отзывчивость здесь улучшилась независимо от ускорения самого process snapshot.

В новом light-прогоне внутренние метрики по трём интервалам:

| Метрика | p95 по интервалам | Максимум за прогон |
|---|---|---:|
| Превышение периода оконного таймера 250 ms | 16,14 / 16,43 / 12,13 ms | 47,54 ms |
| Прикладная часть оконного callback | 0,068 / 0,057 / 0,048 ms | 0,131 ms |

Квантили между интервалами не усреднялись. Во время quiet не было lifecycle-сигналов,
поэтому выборки `queue.wait` нет. Логика очереди и callback timestamps проверена
синтетическими сценариями с искусственно задержанным источником. Прогретый
process snapshot во втором внутреннем интервале: mean 1,031 s, max/p95 1,277 s,
11 наблюдений. Полный опрос остался дорогим, хотя окно в это время отвечает.

RSS в новом off-прогоне: 73,02 → 75,05 MiB, handles 255 → 247; в light:
73,26 → 75,49 MiB, handles 258 → 251. Это короткий прогон, не проверка утечек за сутки.
В обоих случаях integrity=ok, FK errors=0, открытых/отрицательных интервалов=0,
один нормально завершённый run.

## Проверки

Полный набор с включёнными Windows и packaged smoke: **256 passed**.
Ruff check/format и git diff --check прошли. Два предупреждения об устаревающих
интерфейсах в зависимостях FastAPI/Starlette не относятся к переносу потока.
Packaged smoke проверил dashboard в headless Edge, API/PATCH, heartbeat,
целостность/закрытие истории и освобождение HTTP-порта новой сборки.

Новые проверки покрывают медленный poll/resume/startup, последовательность
lock → sleep → wake → sleep, отмену устаревшего process snapshot, выход во время
принятой записи, overflow/recovery, очередь настроек и ошибки worker. Реальный
HWND проверяется с заблокированным источником: WM_NULL, tray Exit, подтверждённый
и отменённый WM_ENDSESSION. Пользовательскую БД тесты не меняли.

Реальные lock/unlock, S3/S0 sleep/wake, fullscreen и длительный 24-часовой сценарий
не выполнялись. Их порядок описан в [performance.md](performance.md).
Этап 4 улучшает отзывчивость; основное снижение CPU ожидается от отказа от частого
полного process poll на этапе 5. Оптимизация state/SQLite остаётся отложенной.

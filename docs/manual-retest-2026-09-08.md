По описанию пользователя run 2 завершён через Ctrl+C, run 3 — через трей.
Сама БД не хранит отдельное поле способа выхода, но подтверждает штатное завершение обоих:

| 3 | 20:05:23.025 | 20:05:51.867 | normal |

Между запусками 12,583 секунды без данных. Сессии не протянуты через этот промежуток.
Восстановление после сбоя не запускалось. В журнале нет ошибок/предупреждений.
`integrity_check=ok`, foreign-key нарушений и незакрытых сессий нет.

Run 2 содержит 365 process, 140 running, 12 foreground и 5 system-state sessions;
run 3 — соответственно 347, 136, 6 и 1. Отрицательных интервалов или выходов за

## Блокировка

В run 2 LOCKED записан с 20:03:58.276 до 20:04:23.350, foreground закрыт
на границе блокировки. Уведомление unlock пришло в 20:04:18.869, а ACTIVE открыт
после свежего snapshot в 20:04:23.350. Таким образом, подтверждённый интервал
блокировки включает 4,481 секунды ожидания чтения snapshot после уведомления.

## Сон: подписка работает, точность ещё требует доработки

В журнале обоих запусков есть подтверждение регистрации power notifications.
В run 2 записан SLEEP **20:04:27.758–20:04:34.600**, длительность **6,842 секунды**.
Уведомления: sleep в 20:04:27.758, первый wake в 20:04:27.911 и повторный wake
в 20:04:34.629. Первое wake обрабатывалось с полным snapshot; его завершение
задало границу SLEEP → ACTIVE. Это следует из кода `CollectionController._resume()`
и `WindowsProvider.snapshot()`, а также соответствующих записей журнала.

Kernel-Power показывает иную последовательность Modern Standby:

| Вход (506) | Выход (507) | Длительность |
|---|---|---|
| 20:04:27.458 | 20:04:27.888 | 0,430 с |
| 20:04:27.889 | 20:04:37.102 | 9,213 с |

Всего **9,643 секунды**, на **2,801 секунды больше**, чем SLEEP в БД.
Получение уведомлений исправлено, однако текущие границы отражают приостановку
desktop-приложения и окончание чтения snapshot, а не полную последовательность
Modern Standby из системного журнала. Нельзя считать проверку точности сна пройденной.

Microsoft отдельно отмечает, что время доставки resume относительно выхода из
Connected Standby не гарантировано: [Desktop Activity Moderator](https://learn.microsoft.com/en-us/windows/win32/w8cookbook/desktop-activity-moderator).
Для устранения расхождения нужно отдельно уточнить источник границ Modern Standby
и отделить их от момента готовности свежего foreground/process snapshot. Простое
перенесение конца SLEEP на первое wake тоже неверно для этого теста: сразу после
первого выхода система снова вошла в Modern Standby.

При этом прежнее окно не продолжалось через сон: foreground отсутствует
с 20:04:27.589 до 20:04:40.385. Ошибка влияет прежде всего на распределение
системного времени и последующее исключение сна из running-статистики.

## Исправление после проверки

Добавлен источник `PowerHistory`: на S0-системе завершённые пары Kernel-Power
применяются с собственными timestamps к текущему run, независимо от DAM callbacks
и скорости чтения процессов. Тест с последовательностью выше теперь получает
ровно 9643 ms SLEEP. Быстрый snapshot lock/idle отделён от полного process/foreground
snapshot. История run 2 и run 3 сохранена без изменений. Для проверки доставки
новых событий на устройстве нужен ещё один ручной цикл сна/пробуждения.

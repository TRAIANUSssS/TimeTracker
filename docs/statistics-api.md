# Статистика и локальный API

Этап 4 реализован поверх схемы SQLite v1, без изменения сырых исторических данных.
Запуск `python -m time_tracker --track` поднимает API на `http://127.0.0.1:8765`.
`--api-port 8766` меняет порт. Занятый порт вызывает явную ошибку запуска;
адрес сервера записывается в `logs/tracker.log`. Выход из трея или Ctrl+C
останавливает HTTP-сервер и трекер. Dashboard — этап 5.

## Контракты

OpenAPI доступен на `/openapi.json`, интерактивная документация — `/docs`.
У всех `/stats/*` обязательны `date_from`, `date_to` и IANA `timezone`.
Даты имеют формат `YYYY-MM-DD` и включены с обеих сторон. `time_from` по умолчанию
`00:00`, `time_to` — `24:00`; точность до минуты. Неизвестная timezone,
неверный формат, обратный диапазон дат или одинаковые времена возвращают `422`.
Поддерживаются годы 2–9998, чтобы преобразование крайних дат не переполняло datetime.

| Endpoint | Результат |
|---|---|
| `GET /stats/apps` | `has_tracking_data`, `has_running_data`, полный список `items` |
| `GET /stats/system` | `active_ms`, `idle_ms`, `locked_ms`, `sleep_ms` |
| `GET /stats/context-switches` | `context_switches` |
| `GET /stats/timeline` | Массив application/system/other/unknown/no_data сегментов; одна дата |
| `GET /stats/activity` | Массив часовых ячеек; минимум две даты |
| `GET /applications` | Все приложения, включая ignored, и текущие параметры |
| `PATCH /applications/{id}` | Обновлённое приложение после применения команды |
| `GET /applications/{id}/icon` | Существующий PNG из кеша или `404` |

Форматы ответов соответствуют §30 ТЗ. Списки приложений не ограничиваются десятью
строками. При `active_only=true` остаются строки с положительным `active_ms`,
сортировка по убыванию активности. При `false` фильтр и сортировка используют
`running_ms`. При равенстве длительностей порядок задаёт `application_id`.
Этот флаг не меняет system, context switches или визуализации.

## Временные окна и расчёты

`domain/time_windows.py` переводит выбор для каждой локальной даты в набор
непересекающихся полуоткрытых UTC-интервалов. Конец `24:00` — следующая полночь;
`23:59` остаётся точной исключённой границей. Ночное окно `22:00–03:00`
включает утро следующего дня даже для последней выбранной даты.

ZoneInfo с установленной tzdata задаёт смещения. UTC-диапазон около каждой даты
разбивается на участки постоянного смещения; граница перехода уточняется до
миллисекунды между часовыми пробами. Для правил IANA это учитывает переходы
на час, полчаса, исторические изменения в секундах и пропущенные календарные даты.
Локальный выбор пересекается с каждым участком независимо: повторяющиеся
02:15–02:45 дают два отдельных интервала, а отсутствующее время не сдвигается.
Результаты объединяются без двойного учёта. Длительности вычисляются в UTC.

`storage/stats.py` читает сессии выбранного диапазона одним SQLite snapshot.
Каждый HTTP-запрос фиксирует один `now_ts`; открытые интервалы заканчиваются
на нём. Future не начисляется. Чтение не выполняет recovery или миграции.

- `active_ms` приложения = foreground ∩ ACTIVE ∩ выбранные окна.
- `running_ms` = running ∩ (ACTIVE | IDLE | LOCKED) ∩ выбранные окна.
- Общее активное время и heatmap = ACTIVE ∩ выбранные окна, включая ignored/unknown.
- `has_tracking_data` учитывает любое известное состояние, в том числе SLEEP.
- `has_running_data` вычисляется для не-ignored приложений до `active_only`.

Интервалы объединяются до суммирования. Для многократных запросов покрытия
часовых ячеек используются префиксные суммы, без повторного обхода всей истории
для каждого часа. SQL ограничивает чтение временными границами запроса;
расчёты интервалов выполняются в Python. Таблица aliases остаётся основой
для будущего объединения приложений; разрешение aliases в MVP не включено.

Context switches считаются в момент начала новой foreground session. Цепочка
пропускает ignored и пустые сессии; смена title/HWND внутри приложения не считается.
Учитывается предшествующее не-ignored приложение перед нижней границей фильтра,
но переход должен попасть в выбранное ACTIVE. Между разными tracker runs цепочка
сбрасывается: новый запуск не является наблюдавшимся переключением приложения.

## Timeline и heatmap

Timeline возвращает абсолютные timestamps. IDLE/LOCKED/SLEEP представлены
отдельно. При ACTIVE неизвестное окно становится `unknown_activity`, ignored —
`other_activity` без имени, ID и title. Пробел в прошлой истории становится
`no_data`, будущее остаётся пустым. Соседние одинаковые визуальные сегменты
могут объединяться, но никогда не перекрывают пробел или невыбранное время.

Маркер новой даты — задача отрисовки этапа 5: серая линия на локальной полуночи,
а не дополнительный временной сегмент. Ответ остаётся массивом по ТЗ. UI должен
располагать сегменты по UTC и форматировать подписи в выбранной timezone;
у повторяющихся часов показывать offset в tooltip.

Для 2–14 дней heatmap содержит строку на дату начала окна. Часы после полуночи
имеют `day_offset=1` и фактическую `local_date`. Поля `window_ms`, `tracked_ms`
и `active_ms` различают выбранную, наблюдавшуюся и активную длительности.
Интенсивность = active/window; отсутствующий DST-час имеет `null`, статус
`missing_hour`. Остальные статусы — `data`, `no_data`, `future`.
`hour_occurrences` показывает число реализаций выбранной части часа, включая
частичное повторение при сдвиге на полчаса.

Для >14 дней группировка идёт по ISO weekday даты начала окна, day_offset и hour.
`average_active_ms` = total_active/sample_days, интенсивность = total_active/total_window.
Даты без наблюдений входят в знаменатель; полностью отсутствующий час не входит
в sample_days. Повторившийся час остаётся одним днём с увеличенным window_ms.

## Запись параметров

`PATCH` принимает только `ignored` и `track_titles`, хотя бы одно поле.
Допустимы JSON boolean; `null`, числа, строки, пустой объект и неизвестные поля
возвращают `422`. Несуществующий ID возвращает `404` при работающем writer.

HTTP-поток помещает команду в ограниченную очередь `SettingsMailbox`.
Таймер скрытого окна Windows обрабатывает очередь на потоке владельца трекера,
последовательно с polling/системными событиями. `SessionManager` применяет
изменение транзакционно и публикует RAM после commit. Только после этого
HTTP-запрос получает `200`. Существующая title policy закрывает текущую сессию
на границе изменения; прежние titles остаются в истории.

Если трекер не принял команду за 10 секунд, она отменяется и возвращается `503`;
позднее такая команда не записывается. Если выполнение уже началось, запрос
дожидается результата транзакции. При выходе ожидающие команды отклоняются.
Ошибка SQLite возвращает `503` с сохранением атомарности БД/RAM.

Сервер доступен только через loopback; Host ограничен localhost/127.0.0.1,
запросы браузера с чужого origin отклоняются. CORS и авторизация не добавлены.
Будущий dashboard следует обслуживать с того же origin. Статистика не кешируется
браузером, поэтому ручное обновление получает новый snapshot.

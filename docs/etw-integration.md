# ETW → worker → SessionManager

2026-09-10. Подключение реализовано как явно включаемый режим. Без флага приложение
использует прежний опрос. Установка сборщика, повышение прав приложения и автозапуск
не выполняются. Источник — отдельный [ETW-сборщик](etw-collector.md).

## Проверка всей цепочки на отдельной БД

В повышенном PowerShell того же пользователя:

```powershell
cd E:\Projects\TimeTracker
.\.venv\Scripts\python.exe tools/run_etw_collector.py --seconds 30
```

В течение 30 секунд в обычном терминале VS Code:

```powershell
.\.venv\Scripts\python.exe tools/check_etw_integration.py
```

Это новый тест интеграции, не повтор проверки доступности источника. Он запускает
настоящий WindowsProvider, CollectionWorker и SessionManager, автоматически создаёт
два коротких процесса, ждёт остановки сборщика, проверяет fallback и завершает worker.
Длительность сессий сравнивается с GetProcessTimes, допуск 2 ms на округление и
разницу ETW timestamp с фактическим завершением. Ожидается одна сессия на помощника
с известным executable. Проверяются SQLite integrity_check и foreign_key_check.

Все данные находятся в новом каталоге `build/etw-integration/<timestamp-id>`:
`tracker.db`, `report.json`, `performance.jsonl`. Report не содержит путей чужих
процессов; тестовая БД содержит обычную историю сбора, включая пути/foreground.
Источник и трекер используют обычное окружение пользователя; тест не блокирует ПК
и не инициирует сон. Во время проверки достаточно оставить ПК включённым.

`reader_and_worker_cpu_seconds` включает worker и контрольный код теста, запуск и
остановку runtime; CPU внешнего ETW-сборщика в это поле не входит. Профиль разбивает
работу по стадиям. Итоговый A/B-замер общего CPU ещё предстоит, после live-приёмки.

## Запуск приложения с событиями

В повышенном терминале запустить сборщик с подходящей длительностью, например
`tools/run_etw_collector.py --seconds 3600`. В обычном терминале:

```powershell
.\.venv\Scripts\python.exe -m time_tracker --track --process-events default
```

Канал должен совпадать с `--channel` сборщика; по умолчанию это `default`.
Получатель только один: приложение и `check_etw_*` нельзя подключать одновременно
к одному каналу. После истечения времени сборщика приложение продолжит опрос.
Для устойчивого автозапуска отдельного сборщика ещё нужен согласованный способ установки.
HKCU-автозапуск не начинает автоматически передавать новый флаг.

## Обработка и восстановление

- Обычный reader thread читает pipe, проверяет протокол и складывает записи в
  ограниченную очередь 4096. Runtime и SQLite доступны только потоку CollectionWorker.
- При включённом источнике reader запускается до начального сканирования. Run
  начинается с быстрого пользовательского snapshot; полный список читается сразу
  в первом tick. Поэтому полученные короткие процессы во время сканирования можно
  записать в уже начавшийся run. До открытия источника полного покрытия нет.
- Новая генерация либо изменение здоровья источника вызывает внеплановую сверку.
  При здоровом источнике интервал полного списка — 60 s, при отсутствии/отказе — 5 s.
  Ошибка самого snapshot повторяется через 5 s. Heartbeat/idle/foreground остаются
  на своих прежних интервалах. Wake/unlock по-прежнему требуют свежего snapshot.
- Таймаут потока — 5 s, переподключение — через 5 s. Overflow, пропуск sequence,
  ошибка identity/пути или протокола отключают использование этой генерации.
  Нельзя восстановить пропущенные короткие процессы простым snapshot; fallback
  ограничивает дальнейший ущерб, но не обещает воспроизвести неизвестную историю.
- Запись, уже извлечённая из reader, остаётся в pending-очереди controller до
  успешной обработки. При прерывании для lock/sleep/stop checkpoint её не теряет.

`ProcessBoundaryRecorded.observed_at` — время обработки, которое не уменьшает
общий watermark. `boundary_at` — исходное время процесса. Такие события уточняют
историю атомарно, не передавая устаревшее observed_at обычному обработчику.
Сохраняются отдельные process_sessions, в том числе закрытая сессия для процесса,
который уже завершился до доставки событий. Start/stop допускаются в обратном
порядке и повторно, с сопоставлением PID + creation time. Поздний start не оживляет
экземпляр, отсутствующий в более свежем полном snapshot, а старый stop не закрывает
новый процесс с тем же PID. Границы ограничены текущим run и покрытием источника.

Поле detected_at может быть уточнено назад до подтверждённой границы в пределах
покрытия; это не время доставки. Затронутый суффикс application_running_sessions
пересчитывается как объединение интервалов процессов, без двойного времени для
параллельных экземпляров. Незатронутый префикс сохраняется. Сессии продолжают
учитываться при IDLE/LOCKED; сырое running при SLEEP отделено от системного состояния,
как и в прежней модели статистики.

Identity в текущей БД имеет точность миллисекунд. ETW преобразуется тем же способом,
что и psutil Windows (100-ns ticks → double seconds → round(ms)); тест сверяет
результат с настоящим процессом. Обнаруженная коллизия разных ETW CreateTime в одной
миллисекунде делает поколение неполным, вместо объединения экземпляров. Проверка
последних identity ограничена 4096 PID.
Основание преобразования: [psutil Windows init.c](https://github.com/giampaolo/psutil/blob/release-7.2.2/psutil/arch/windows/init.c).

## Миграция и границы текущей реализации

Схема БД обновляется с 1 до 2 при следующей инициализации новой версией программы.
Добавляется nullable `foreground_sessions.process_session_id` и два индекса.
Старая история сохраняется, существующие строки получают NULL. Старый exe со
схемой 1 такую обновлённую БД открыть не сможет; тестовая проверка использует
свою отдельную БД. Рабочая БД пользователя в ходе разработки не открывалась.

Новые foreground-сессии привязаны к процессу. Поэтому поздний stop корректирует
даже уже закрытый foreground нужного экземпляра. При смене процесса с теми же
HWND/title создаются соседние интервалы: старая привязка не переносится на новый PID.
Неизвестные PID без подтверждённой creation time остаются ограничением snapshot.

ETW может доставлять события с задержкой около двух секунд. Поэтому обычный выход
теперь запрашивает остановку сборщика и дочитывает остаток до закрытия run — см. раздел
«Финальная доставка при выходе приложения». Первоначальный live-тест проверял другой
порядок: сборщик сначала останавливался по таймеру, затем завершался worker.
Новый порядок проверен через `--stop-early`: `20260910T175813Z-b17c2c4e`, passed=true.

## Финальная доставка при выходе приложения

Worker фиксирует время завершения учёта, затем reader отправляет `finish` для текущего
поколения. Сборщик останавливает собственную ETW-сессию, дожидается consumer, отправляет
все `draining` и заключительный `stopped`. В нём проверяются `cleanup_confirmed`,
`data_complete`, непрерывность последовательностей и итоговый `last_sequence`.
Worker сохраняет оставшиеся события через SessionManager и только затем закрывает run.
События после зафиксированной границы не добавляются; ожидание не увеличивает учтённое время.

Бюджет ожидания/обработки — 20 s, проверяется между операциями. Уже выполняющийся
вызов SQLite/Windows и закрытие reader могут увеличить фактическое время выхода.
При тайм-ауте, разрыве, потере данных или отсутствии финального подтверждения run
закрывается с `exit_reason=events_incomplete`, в журнал пишется предупреждение.
Уже сохранённые данные остаются. Если ETW вообще не подключался, обычный polling run
завершается без ожидания подтверждения. При завершении сборщика по его таймеру
полученный остаток также дочитывается. Во время выхода переподключения прекращаются.
Принудительное убийство процесса и ограниченный Windows срок выключения ПК не дают
такой же гарантии, как обычная команда выхода.

Автотесты `test_etw_shutdown.py` используют настоящий Windows pipe, worker и отдельную
SQLite. Проверены 80 событий, доступных только после остановки consumer, несколько
пачек, сохранение исходной границы времени, pending controller, завершение по таймеру,
гонка ready/finish, разрыв, тайм-аут, старый протокол и неверные команды/подтверждения.
Реальная ETW-подписка и разница уровней прав в этих тестах не моделируются.

Локальная проверка этого изменения: 16 сценариев завершения, полный набор
`334 passed, 2 skipped`; обе opt-in проверки затем выполнены отдельно —
`2 passed` (Windows live и packaged live). Изолированная сборка:

Инструмент сам запускает два коротких процесса и запрашивает завершение worker сразу
после их выхода, до истечения времени сборщика. Ручные клики не нужны. Проверяются
точность интервалов через GetProcessTimes, SQLite, `shutdown_complete=true`,
`finish_requested=true` и нормальное закрытие run. `shutdown_events` показывает число
событий, обработанных на выходе, но само по себе не доказывает, что они находились именно
в буфере ядра. Отчёт — `build/etw-integration/<timestamp-id>/report.json`.

Для следующей проверки устойчивости автоматизируются контролируемые сбои и нагрузка.
Реальные сон/пробуждение и длительная повседневная работа потребуют участия пользователя;
сбор метрик и проверку БД выполняют инструменты. Пакетная запись SQLite остаётся отдельным
кандидатом по результатам профиля, а общий CPU сравнивается на одинаковых сценариях.

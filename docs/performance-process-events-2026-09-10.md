# Этап 5: прототип источника событий и проверка прав

Дата: 2026-09-10. Исходная версия — `db4e6db` (очередь и поток-владелец).
**Этап 5 пока не завершён:** обычному запуску отказано в доступе. Повышенный запуск
подтвердил реальную доставку WMI и ETW. Для дальнейшей интеграции выбран ETW:
в проверенных событиях есть точная identity и близкие к реальным границам timestamps.
Доставка буферизуется на 1,5–1,9 s. Переход на reconciliation 60 s не включён.

После выбора источника реализован [отдельный ETW-сборщик и локальный клиент](etw-collector.md).
Интеграция в SessionManager остаётся следующим изменением. Транспорт между
повышенным сборщиком и обычным клиентом прошёл live-проверку
`20260910T163358Z-2318677c`: 229 событий без зарегистрированных потерь,
обе пары помощников с точной identity, штатная остановка и cleanup.

## Выполнено

Добавлен диагностический `diagnostics/process_events.py`: временная semisynchronous
WMI-подписка на `Win32_ProcessTrace` либо отдельно StartTrace/StopTrace,
нормализация событий в неизменяемые скалярные данные, конечный timeout NextEvent,
различение таймаута и отказа источника, освобождение COM на потоке-владельце.
Запросы не используют intrinsic `WITHIN` polling. Это прототип, он не подключён
к runtime, не читает executable/metadata и не пишет SQLite.

`tools/probe_process_events.py` проверяет каждую подписку в отдельном ограниченном
по времени процессе. При успешном подключении запускает собственные невидимые
процессы с жизнью 0,3 и 2 секунды, проверяет доставку start/stop и сохраняет их
timestamps. Записывает CPU probe и доступных WmiPrvSE до/во время подписки, отмечая
неполный доступ или изменение состава WMI-хостов. События чужих процессов учитываются
только агрегированными счётчиками, без имён, путей и командных строк.

Первоначальный прототип проверял создание временной real-time ETW-сессии с provider
`Microsoft-Windows-Kernel-Process`, keyword PROCESS `0x10`, level 4. Использует
`logman ... -ets`: без сохранённого Data Collector Set и ETL-файла. Имя уникальное,
в finally выполняется остановка только своей сессии. Это проверка возможности
старта, не реализация ETW consumer и не замер его эффективности.

После повышенного запуска добавлен `diagnostics/etw_process_events.py`: настоящий
real-time consumer OpenTrace/ProcessTrace с TDH-декодированием по именам свойств.
Обновлённый probe (`schema_version=2`) проверяет доставку ETW start/stop собственных
помощников, наличие CreateTime/ImageName и совпадение CreateTime с GetProcessTimes.
Очередь ограничена 4096 записями, overflow и ошибки декодирования видимы в отчёте;
BufferCallback учитывает потери, сообщённые ETW. Пути и командные строки чужих
процессов не сохраняются, ImageName преобразуется в признак доступности.
Таймер сброса ETW-буферов — 1 s: время события и задержка доставки измеряются раздельно.
Контроллер останавливает свою сессию, consumer дочитывает буферы и закрывает handle.
Дочерний процесс с consumer ограничен timeout; родитель повторяет cleanup в finally.
Реальная доставка подтверждена повышенным запуском `20260910T160827Z-79559315`.

Для WMI добавлены actual creation/exit timestamps через retained handle собственного
помощника и признак, жив ли он при чтении события. В старой версии длительность
`sleep(0.3)` была только заданным ожиданием, а не измеренным временем жизни процесса.

## Повторный повышенный запуск: выбор ETW

Артефакт: `build/process-events/20260910T160827Z-79559315/report.json`, elevated=true,
schema_version=2. Все WMI-подписки и ETW получили ожидаемые события помощников.

| Показатель ETW | Результат |
|---|---:|
| Получены start/stop собственных помощников | 4 из 4 |
| CreateTime совпал с GetProcessTimes | 4 из 4 |
| Фактическая жизнь помощников | 354,672 / 2046,658 ms |
| Отклонение timestamp start от создания | +0,021–0,026 ms |
| Отклонение timestamp stop от завершения | +0,134–0,155 ms |
| Доставка от реальной границы процесса | 1534,740–1889,343 ms |
| Потерянные события / буферы | 0 / 0 |
| Ошибка consumer | нет |
| Cleanup своей сессии | подтверждён |

Это проверка двух процессов на данной системе, не гарантия полноты или задержек
под нагрузкой. В start версии 4 присутствовал ImageName; в stop версии 2 у помощников
его нет. Счётчик `missing_ImageName=8` сам по себе не означает потери событий:
путь следует сохранять при start, а stop связывать по PID и CreateTime.
Повторный stop родителя вернул «сессия не найдена», поскольку её уже успешно
остановил дочерний consumer; `cleanup_confirmed=true` это учитывает.

У WMI короткий помощник уже завершился к моменту чтения start. Отклонение
TIME_CREATED от измеренной границы в этом прогоне достигает 2,653 s. Поэтому
выбран ETW: он позволяет получить исходную identity и время события даже после
завершения процесса. Дополнительный прогон для выбора доступного источника не нужен.

Буферизация ETW остаётся существенной: нельзя подменять время события временем
доставки. Например, start и stop процесса длительностью 355 ms пришли практически
вместе. Текущий SessionManager отбрасывает события старше last_event_at; простая
передача этих записей в существующую очередь потеряет историю, а выравнивание
обоих времён по моменту обработки сократит её почти до нуля. Интеграция должна
отдельно обеспечить обработку запоздавших границ процессов.

`probe_cpu_seconds=0.0` не означает бесплатный ETW: короткий замер ограничен
разрешением CPU-часов и не включает запуск, остановку и дочитывание consumer.
Снижение CPU приложения ещё не измерено. При приёмке нужны сопоставимые прогоны
polling и events с учётом CPU отдельного сборщика, запуска/остановки, частых стартов,
потерь, памяти и handles.

## Первый повышенный запуск: предварительный результат

Артефакт: `build/process-events/20260910T155153Z-f3bb5200/report.json`, elevated=true.
Все три WMI-подписки открылись и получили все ожидаемые события помощников.
Общий Trace получил обе пары start/stop, отдельные подписки — соответствующие
два события каждой. ETW start/stop вернули 0, cleanup подтверждён.

| Показатель | Результат |
|---|---:|
| WmiPrvSE без подписки | 0,849% всей машины |
| WmiPrvSE с общей / start / stop подпиской | 0,810 / 0,805 / 0,921% |
| CPU probe с общей / start / stop подпиской | примерно 0,098 / 0,058 / 0,134% |
| Доставка start от creation time процесса, 4 события | примерно 1,31–1,37 s |
| Чтение start от WMI TIME_CREATED | примерно 5–29 ms |

Значительная часть задержки находится до TIME_CREATED WMI: это timestamp генерации
события, не точная граница создания процесса. Наивная оценка по received−TIME_CREATED
скрыла бы задержку около 1,3 s. Короткий процесс к моменту разрешения PID может уже
завершиться; наличие его события само по себе не гарантирует получение executable.
Полное время жизни и точный момент завершения помощников старый probe не измерял.

Замеры по 10 s слишком короткие для утверждения о стоимости WMI. Фоновую нагрузку
WmiPrvSE нельзя целиком приписывать подписке. Снижение CPU всего TimeTracker ещё
не измерено: production-интеграция отсутствует.

## Воспроизведение

```powershell
.venv/Scripts/python.exe tools/probe_process_events.py --seconds 10
```

Каждый запуск создаёт отдельный каталог `build/process-events/<timestamp-id>`.
Отчёт сохраняется после каждой проверки. WMI child ограничен timeout; при успешной
подписке чтение длится указанное время. Код выхода probe 0 означает, что диагностика
завершилась: доступность источника определяется полями `subscribed`, `hresult`,
`all_helper_events_received`, а для ETW — `start.exit_code`. Это не приёмочный тест.
`cleanup_confirmed=false` требует проверить указанную в отчёте уникальную сессию.

## Проверки и ограничения прототипа

21 тест прошёл: 13 для WMI и 8 для ETW/probe. Проверены HRESULT в COM wrapper,
timeout/ошибка, владение потоком и cleanup,
повторная попытка после отказа, допустимые поля/классы и точность FILETIME.
Проверено, что время генерации события не объявляется creation time процесса.
При PID reuse stop и start могут доставляться в обратном порядке: нормализатор
сохраняет исходное и время получения, но не обещает разрешить identity самостоятельно.
Ruff check/format и git diff --check проходят.

ETW-проверки включают размеры/смещения ctypes-структур, TDH-декодирование start/stop,
переполнение очереди, ошибку callback, счётчики потерь, закрытие consumer при
отсутствующей сессии, GetProcessTimes после завершения помощника и расчёт задержек.

Интеграция очереди process events, сведение начального snapshot с буфером событий,
защита от позднего stop, reconnect/fallback и 60-секундная сверка остаются задачами
после проверки прототипа. Реальная доставка ETW подтверждена, но production-путь
и восстановление после потерь ещё не реализованы.

## Решение для продолжения

Текущий portable-трекер работает без обязательного повышения прав. Оба проверенных
варианта не подходят для незаметной замены polling в таком режиме на этом ПК.
Windows разрешает управление ETW-сессиями администраторам, некоторым службам и
участникам Performance Log Users; права конкретного провайдера/сессии всё равно
нужно проверить. [Microsoft: StartTrace](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracea).

Рекомендуемый следующий путь — отдельный ETW-сборщик с необходимыми правами и
передача событий обычному приложению через локальный канал с проверкой доступа.
Диагностический запуск пользователя не устанавливал такой сборщик и не выдавал
приложению постоянных прав. Установка/автозапуск ещё не согласованы и не изменены.

Порядок дальнейшей реализации:

1. Сборщик сохраняет исходные timestamps, PID/CreateTime и путь из start; передаёт
   события и состояние источника через ограниченную очередь. Проверяются версии
   схемы, потери, завершение источника и освобождение собственной ETW-сессии.
2. Поток-владелец сводит начальный snapshot и события, обрабатывает поздние границы
   без обнуления коротких сессий и без закрытия нового процесса старым stop.
3. Здоровый источник разрешает reconciliation 60 s; ошибка/потери вызывают
   внеплановую сверку и fallback 5 s. После wake/reconnect нужна полная сверка.
4. Автоматические сценарии проверяют короткие процессы, PID reuse, задержку и
   перестановку событий, переполнение, отказ источника и restart. Сравнительный
   замер учитывает CPU трекера и сборщика вместе. Ручная проверка остаётся для
   реального lock/sleep/wake и согласованного способа автозапуска.

Если отдельная настройка прав окажется неприемлемой, запасной путь — более дешёвый
массовый снимок Windows без повышения прав, с сохранением ограничений polling.

# Замеры производительности

Диагностика добавлена отдельно от оптимизаций: интервалы опроса, identity,
правила сессий и записи SQLite сохранены. Начать можно полностью автоматически.

## Что выполняется автоматически

Runner `tools/benchmark_tracker.py` создаёт уникальный каталог в `build/benchmarks`,
запускает приложение с отдельной БД и свободным API-портом, ждёт готовности,
отделяет прогрев, измеряет процесс раз в секунду и штатно закрывает его через
собственное окно TimeTracker. Затем проверяет целостность тестовой БД, внешние
ключи, закрытие сессий, отрицательные интервалы и штатное завершение run.

В Windows `.venv/python.exe` может быть launcher. Runner находит рабочий процесс
по окну TimeTracker среди потомков запущенного экземпляра; его PID и creation time
сохраняются в summary. При каждом измерении identity проверяется свежим объектом
psutil. Завершение распространяется только на запущенный runner экземпляр.

Текущая пользовательская БД не используется. Тестовая БД содержит обычные
наблюдения рабочего стола; JSONL диагностики содержит только числовые агрегаты
и технические названия стадий, без заголовков окон и путей приложений.

Сценарий `quiet` не отправляет ввод и не меняет foreground. Можно продолжать
пользоваться ПК; для сравнения версий желательно выполнять одинаковую работу
и не запускать сборку/антивирусную проверку одновременно с замером.
При отсутствии ввода приложение естественным образом перейдёт в IDLE.
Runner не имитирует ACTIVE и отдельно показывает фактически наблюдённые состояния.

## Команды из корня проекта (PowerShell)

Быстрая повторяемая проверка: 3 пары по 2 минуты, прогрев 15 секунд перед каждым
замером. Порядок off/light чередуется; общее время около 14 минут с запуском.

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --duration 120 --warmup 15 --repeats 3 --modes off light
```

Полный протокол: 3 пары по 10 минут, прогрев по 30 секунд (около 65 минут):

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py
```

`off` — без внутренних таймеров, внешнее наблюдение остаётся; `light` — общие
стадии; `detail` — дополнительно отдельные обращения к данным процессов.
Сравнение off/light оценивает добавочную стоимость включённой диагностики.
Это не сравнение с исходной версией до добавления диагностических обёрток.

Короткий подробный разбор коллектора без БД и иконок:

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --micro --snapshots 5
```

Первый snapshot имеет холодный кеш metadata в памяти; следующие — прогретый.
Дисковый кеш Windows не очищается. Подробный режим используется для поиска
дорогих стадий, а не как итоговый показатель нагрузки обычной сборки.

Контролируемый запуск коротких и длинных фоновых процессов (без видимых окон):

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --scenario churn --duration 60 --warmup 5 --repeats 1 --modes light
```

Каждые 10 секунд создаётся тестовый Python-процесс, поочерёдно на 0,3 и 7 секунд.
Его PID, creation time и найденные в тестовой БД process-сессии попадают в summary.
Текущий polling может пропускать короткие процессы; это зафиксированный предел
метода, а не ошибка диагностики. Ожидаемую длительность helper нельзя считать
точным фактическим временем завершения — это параметр сценария.

Для portable exe (сначала собрать версию, содержащую новые флаги):

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --executable dist/TimeTracker/TimeTracker.exe --duration 120 --repeats 1 --modes off light
```

Внешнее наблюдение уже работающего процесса, без его остановки:

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --pid 12345 --duration 600
```

Здесь нужен PID самого приложения, а не launcher. Состояние показывается как
UNOBSERVED, поскольку runner не открывает его пользовательскую БД.
Внутренние таймеры в уже запущенном процессе этой командой не включаются.

Для длительной ручной проверки внутреннюю диагностику можно включить при запуске:

```powershell
.venv/Scripts/python.exe -m time_tracker --track --perf build/manual-perf.jsonl
```

Это обычный запуск трекера с обычной БД. Предварительно завершить предыдущий
экземпляр; существующая защита от второго writer остаётся. Путь perf должен быть
новым: отчёт никогда не перезаписывается. `--perf-detail` добавляет подробные стадии.
Обычная работа без этих флагов не создаёт perf-файлов.

## Файлы результата

- `environment.json`: версия, commit/dirty, Windows, CPU, Python и psutil.
- `configuration.json`: параметры нового прогона.
- `samples.jsonl`: внешние замеры CPU, RSS, threads, handles, I/O с фактическим временем.
- `performance.jsonl`: внутренние агрегаты каждые примерно 60 секунд и при выходе.
- `summary.json`: средний CPU, CPU seconds/minute, распределение секундных замеров,
  состояния, стартовые затраты, ресурсы и результат проверки БД.
- `failure.json`: причина неуспешного прогона, если он не завершился.
- `tracker.db`, `logs`, `icons`: изолированные данные тестового экземпляра.

Создать читаемый Markdown-отчёт из завершённого каталога:

```powershell
.venv/Scripts/python.exe tools/report_benchmark.py build/benchmarks/ИМЯ_КАТАЛОГА
```

Результат — `report.md`. Генератор читает только JSON/JSONL, не запускает сбор
и не меняет тестовую БД. Полные сырые отчёты остаются в игнорируемом `build`;
выводы и выбранные результаты можно сохранить в `docs`.

## Как читать цифры

CPU нормализован на все логические процессоры:
`100 × CPU seconds / elapsed seconds / logical CPU count`.
На машине с 16 логическими процессорами одно занятое ядро — около 6,25%.
Среднее взвешивается по реальному времени; оно не равно среднему показаний
диспетчера задач, снятых вручную в произвольные моменты.

Wall time показывает длительность операции вместе с ожиданием. Thread CPU
показывает процессорное время текущего потока; отдельно измеряется весь процесс.
Вложенные стадии содержат inclusive и exclusive значения. Складывать inclusive
времена разных уровней нельзя. CPU других потоков и накладные расходы диагностики
могут остаться за пределами измеренных стадий.

Память внутренних выборок ограничена 2048 последними наблюдениями на стадию за
интервал. Count/total/mean/max относятся ко всему интервалу, p50/p95 — к сохранённым
наблюдениям; размер выборки указан явно. Глобальный p95 не вычисляется усреднением
интервальных p95. Короткие CPU-операции могут округляться до нуля из-за разрешения
системных часов; диагностировать их лучше по агрегатам.

`sqlite.begin` и `sqlite.commit` включают также создание/освобождение вложенных
savepoints. Счётчик `sqlite.transactions` показывает внешние транзакции;
число `sqlite.commit` нельзя трактовать как число физических синхронизаций диска.

Внутренний отчёт включает запуск, прогрев и остановку, внешний steady-state отчёт
их исключает. Эти окна нельзя напрямую вычитать друг из друга. Состояния ACTIVE/IDLE
размечаются по секундным наблюдениям БД: переходы между замерами не восстанавливаются.

Запись агрегатов выполняется на границе завершённой внешней измеряемой операции;
длинная операция или сон могут задержать выгрузку. Ошибка записи perf-файла отключает
диагностику и не должна прерывать транзакции трекера.

## Что остаётся ручным

Базовый CPU, работа кешей, SQLite, короткие процессы и проверка БД не требуют кликов.
Реальные Chrome/VS Code, fullscreen-видео, блокировку и sleep/wake проверяем отдельным
сценарием, когда это удобно пользователю:

1. Переключить несколько приложений и вкладок, открыть другой документ в том же окне.
2. Войти в fullscreen-видео и выйти, проверить отсутствие заметного подвисания.
3. Дать ПК перейти в IDLE, затем вернуться; отдельно выполнить lock/unlock и sleep/wake.
4. Записать примерное время действий и субъективные задержки для сопоставления с логом.

Автоматический runner не блокирует и не усыпляет ПК. Задержки process events и
нагрузка WmiPrvSE добавляются при прототипе событийного источника;
сейчас WMI-подписок в приложении ещё нет.

Для отдельной проверки доступности источников этапа 5 добавлен
`tools/probe_process_events.py --seconds 10`: три временные WMI-подписки, проверка
прав ETW и CPU доступных WmiPrvSE. Он не подключён к трекеру и не меняет его БД.
Отказ доступа явно сохраняется в отчёте. См.
[результат прототипа](performance-process-events-2026-09-10.md).

Для проверки отдельного ETW-сборщика с обычным получателем добавлены
`tools/run_etw_collector.py` и `tools/check_etw_collector.py`.
Получатель сам запускает помощников, проверяет identity/start/stop/потери и сохраняет
отчёт. Команды двух терминалов и границы CPU-замера — в
[инструкции сборщика](etw-collector.md). Этот smoke пока не измеряет ускорение трекера.

`tools/check_etw_integration.py` проверяет цепочку до SQLite на отдельной БД,
сохраняет `performance.jsonl` и CPU reader + worker. После запуска повышенного
сборщика дальнейшие действия автоматические. Команды и границы измерения —
в [инструкции интеграции](etw-integration.md).

## Задержки окна и очереди (этап 4)

Для изолированного запуска доступен внешний probe, одинаковый для старой и новой версии:

```powershell
.venv/Scripts/python.exe tools/benchmark_tracker.py --duration 120 --warmup 10 --repeats 1 --modes off light --probe-window
```

Для portable добавить `--executable PATH`. Runner отправляет `WM_NULL` только окну
своего тестового процесса через `SendMessageTimeout` с timeout 3000 ms. Он не меняет
фокус, не создаёт ввод и не сбрасывает IDLE. RTT записывается в `samples.jsonl` и
summary: count, failures, mean/p95/max успешных проб. Отказы показываются отдельно;
их нельзя интерпретировать как нулевую задержку. Probe выполняется примерно раз
в секунду и при медленном ответе увеличивает интервал внешнего sampling; CPU считается
по фактической длительности. Сравнивать нужно прогоны с одинаковым флагом.
`--pid` с probe не допускается. Метод —
[WM_NULL / SendMessageTimeout](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeoutw).

При `--perf` JSONL дополнительно содержит отдельный объект `latencies`:

- `queue.wait`: от enqueue до начала обработки lifecycle-уведомления worker.
- `window.timer_lateness`: превышение 250 ms между вызовами WM_TIMER. Включает
  задержки планировщика, ОС, GIL, открытое меню и сон; это не чистое время collector.
- `window.callback_duration`: длительность прикладной части callback, включая
  действия меню и финальное ожидание при WM_ENDSESSION.

Для них хранятся count/total/mean/p50/p95/max и последние 2048 samples. Это задержки,
они не суммируются со стадиями выполнения/CPU. Квантили остаются по интервалам.
Callbacks только обновляют агрегаты; выгрузка выполняется worker или при завершении.
Счётчики `queue.enqueued/handled/overflow/recovery/before_baseline/late_notification`
показывают доставку и восстановление. `collector.observation_discarded` и
`collector.startup_snapshot_discarded` означают отмену результата из-за нового сигнала,
включая stop; исключение отмены может попасть в `errors` внешней измеряемой стадии,
но само по себе не является аварией worker. Подтверждение аварии — журнал/exit code.

Ожидание в очереди по-прежнему может длиться столько, сколько текущий системный вызов
или snapshot: поток освобождает message loop, но не прерывает Windows API. Точные
границы lifecycle сохраняются благодаря callback timestamp. Синтетические тесты
проверяют блокировку источника и гонки автоматически; реальные S3/S0, lock/unlock
и длительный пользовательский сценарий остаются отдельной проверкой.
